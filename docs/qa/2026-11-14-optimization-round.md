## 3. 假设与验收规则(写在实现之前)

**H-I 事件记录**
- 假设：加上后，下一轮可以从库里直接算出"每张小票保存前改了几处、改的是哪些字段、从识别到保存多久"。
- 验收：迁移只增不删且幂等(升级路径测试)；`POST /api/scan` 返回 `scanId` 且 `scan_log.duration_ms` 被写入；`POST /api/receipts` 接受可选 `meta`(路由层严格校验，非法形状 400，缺省不影响保存)；端到端：模拟扫描后改一个字段再保存，`save_events` 有 1 行且 `edited_fields` 含该字段名；**隐私测试**：表里任何列都不含商品名、金额或图片；90 天前的行在写入时被清理；`scripts/edit-diff.mjs` 只读，对空库输出"0 行"而不报错。
- 护栏：全部现有测试与端到端绿；保存接口无 `meta` 时行为不变。

**H-R1 差额行**
- 假设：`normalize()` 在税规则之后，若印出的 `total` 比 `subtotal+gst+pst` 多出超过 0.02，加一条明细 `未识别差额(请核对)`，金额 = 差额，taxable 0，分类 其他，并在 `receipt` 上标 `residual_added: true`；餐厅小票的小费会以这种形式出现在核对表里，由人改名或删除。
- 验收(离线重放 `eval/replay.cjs`，24 张首轮)：`consistent` 在餐厅组 0/3 → ≥2/3；`tipFound` 0/4 → ≥3/4(按金额匹配)；**基线里全对的小票没有一张变错**；总额已自洽的小票(costco、tnt、mix、disc 组)上**没有一条**新增差额行；全量测试绿。任一条不满足即放弃并记录。
- 护栏：`subtotal`、`total` 不改；只在 `total` 印出且大于 0 时触发。

**H-R2 日期标记**
- 假设：模型没给出合法日期时，`normalize()` 仍填今天，但 `receipt.date_guessed = true`；`ScanTab` 的日期输入框显示"日期未识别，已填今天，请核对"。
- 验收：重放里 deg-04 被标记，其余 23 张首轮结果都不被标记；端到端：模拟扫描返回无日期时提示出现，返回有日期时不出现；保存接口忽略该字段(不入库)。
- 护栏：任何数值指标不变。

**H-P1 列表去掉 raw_json**
- 假设：`listReceipts` 只选列表需要的列，每次响应体从约 240 KB 降到 ≤ 40 KB；同一份种子数据上 S1 读混合 c=50 的 p50 降 ≥20% 或吞吐升 ≥20%。
- 验收：一次性实例、同一份种子数据、同一台机器、前后各跑一次 S1(c=50，60 s)，报告两组数字与差异；详情接口仍返回 `raw_json`；前端列表没有任何字段缺失(端到端绿)。
- 护栏：不满足 20% 也可以上线(体积下降本身就是收益)，但要如实报告。

**H-P2 统计索引**
- 假设：`receipts` 上缺少 (user_id, purchased_at) / (family_id, purchased_at) 类索引，`EXPLAIN` 显示全表扫描；加索引后约 7,500 张/用户时统计接口 c=1 p50 降 ≥50%。
- 验收：`EXPLAIN` 前后对比；同一份种子数据上前后各测一次；迁移只增不删、幂等，带升级路径测试。若 `EXPLAIN` 显示已经走索引，则放弃并记录。

**H-M 模型对比**
- 假设：`gemini-2.5-flash` 在从未见过的保留集上整张全对比 flash-lite 高。
- 方法：先用 `eval/build-dataset.cjs` 的生成器用新的随机种子生成 **12 张保留集**(生成前不看、生成后不按失败调整)，再对两个模型各跑一次：已有 25 张 + 12 张保留集，共约 74 次调用；记录每次的 token 用量与耗时。
- 验收(建议规则，不改线上)：只有当保留集上 flash 的整张全对多出 ≥3 张，且每次扫描费用 ≤ flash-lite 的 2 倍，才建议切换；否则建议保持。无论结果如何，本轮不改 `.env`。
- 护栏：调用计数文件，硬上限 120(给其他实验留 30)。

## 3b. H-R1b: 差额行的修正(2026-11-15，写在改代码之前)

**起因**：另一个模型的独立审查发现 H-R1 的实现会重复计入。我离线复现了两种形状(测量)：
- A：模型已把小费提成一条明细，小计却照抄印出值(明细 55 + 小费 9.5，subtotal 55，total 67.25) → 又加一条 9.5，明细之和变成 74。
- B：小计读短、明细齐全(明细之和 100，subtotal 88，total 112) → 多加一条 12。设计集里的 deg-04 就是这一类(raw: subtotal 38.88，明细之和 49.76，total 54.98)，只因为它本来就不算全对，没被"回归"检查抓到。
根因：差额用的是模型给的 `subtotal`，应该用**明细之和**。H-R1 的验收第一条在加了差额行之后按构造必然成立，没有检验到这一点。

**假设**：差额 = 印出的 `total` − 明细金额之和 − gst − pst。大于 0.02 时加一条"未识别差额(请核对)"，并把 `subtotal` 设为加完之后的明细之和；不加行时不动 `subtotal`。核对界面在"明细合计 + 税 ≠ 实付"(相差超过 0.02)时实时显示一行提示，这样用户删掉差额行或改金额之后仍能看到对不上。

**验收(任一条不满足就把差额行整个撤掉，只留日期标记)**
1. 单元形状：A → 不加行、明细不变；B → 不加行；C(漏了一条 12 的明细，subtotal 正确) → 加一条 12；D(漏了小费，设计集的形状) → 加一条 9.5 且 subtotal = 64.5；差额为负、`total` 缺失、差额 ≤ 0.02 → 都不动。
2. 重放 `baseline`(24 张，对 main)：基线里全对的小票没有一张变错；餐厅组 `subtotal+gst+pst=total` ≥ 2/3、tipFound ≥ 3/4；每一条差额行都对应 raw 里"total − 明细之和 − 税 > 0.02"的真实差额(逐条列出)；基线里全对的小票不得出现差额行。
3. 重放 `after` 批(模型已把小费提成明细)：rest-01/02/03 与 cn-02 上**不再有**重复的差额行(原实现各多一条)。
4. 重放保留集 `models-lite-holdout`：无回归。这批数据我已经看过结果，不再算"没见过的数据"，只作回归检查。
5. 端到端：模拟扫描带差额行时提示可见；删掉差额行后出现"对不上"的实时提示；补回后消失。全量测试与端到端绿。

**事先说明的局限**：小费被模型填进 pst 的形状(cn-02 类)差额为 0，仍然不会被发现；模型把税填 0 又漏小费时，税与小费会合成一条差额。这两类本轮不处理。

### 违反约束的发现：主机上的构建会对线上库执行迁移

部署前核对时发现，线上库在部署之前已有 `save_events`(创建于 2026-11-15 10:08:34 UTC)和 `scan_log.duration_ms`(10:24:22 UTC)。**[测量]**

- **原因**：`src/db.cjs` 在被导入时就执行 `initSchema()`；`next build` 收集页面数据时会导入它，并读取主检出目录的 `.env`，而 `.env` 指向线上库 `vanspend`(127.0.0.1:3307)。用不存在的库名做构建复现：构建输出了 7 次 `Access denied ... to database 'vanspend_buildprobe_x'`，证明构建期确实连库执行建表。**[测量]** 10:08 正好是整合时在主检出目录跑 `npm run build` 的时间。**[推断]**
- **影响**：两项都是只增不删的迁移，数据行与 11-13 的备份逐字节相同(除了用户已批准删除的 `sessions` 表)。**[测量]** 但这违反了"不对线上做写入、部署前备份"：迁移先于备份落到了线上。之前几轮在主检出目录的构建很可能也是这样，只是迁移随后都被部署了，所以没有显露。**[推断]**
