# 2026-11-14 证据驱动的优化轮(整晚自主运行)

**目标**：对 VanSpend 做一轮只由证据驱动的优化。只在证据支持时改动，没有证据就先收集证据。开放的决定由代理做出并在此记录，用户醒来后可以推翻。

**退出条件(可检查)**
- P1 本文第 0 节列出每一条现有测量，含来源、样本量、局限，并点名没有证据的问题。
- P2 事件记录已合并、已部署；`scripts/edit-diff.mjs` 对线上库只读运行并输出报告。
- P3 第 3 节每个候选改动都有写在实现之前的假设与验收规则；每个改动要么带前后数字上线，要么带原因被放弃。
- P4 `main` 的 CI(单元 + 构建 + 端到端)绿；线上容器 healthy；部署后 41 项线上回归通过；线上库只剩 `admin`。
- P5 最终报告每个结论标注 测量/推断/猜测；决策日志 `docs/qa/decisions-2026-11-14.tsv` 经审计；另一个模型家族的审查意见附在报告末尾。

## 1. 开放问题的决定(用户醒来后可推翻)

| 问题 | 决定 | 理由 | 可以改成 |
|---|---|---|---|

| 先真实使用再优化，还是基于现有测量 | 基于现有测量做这一轮，同时把事件记录建好，下一轮才有真实证据 | 整晚内不会有真实使用 | 等家里人用 N 周再做 |
| 加事件记录 | **加**。`scan_log` 补 `duration_ms`；新表 `save_events`：谁、哪张小票、对应哪次扫描、保存前改了哪些**字段名**、AI 条数与保存条数、从识别完成到保存的毫秒数、时间。**不记录任何值、商品名、金额、图片**。保留 90 天，写入时清理。无界面，只有只读脚本 | 最小可用；字段名足以回答"识别在哪里让人吃亏"，不记值避免二次存储财务数据 | 不加；或改保留期 |
| 用家里人的真实照片评估 | **不用**。现在也没有这类照片。改为生成一组**事先没看过**的合成保留集来降低乐观偏差 | 没有照片；照片含店名金额日期 | 提供照片后下一轮用 |

| 家庭成员可用性测试 | 不做 | 整晚没有人 | 之后做 |
| 时间盒 | 到退出条件满足为止，上限约 8 小时；每个单元先验证再做下一个 | 自主运行 | 缩短 |

## 3. 假设与验收规则(写在实现之前)

**H-I 事件记录**
- 假设：加上后，下一轮可以从库里直接算出"每张小票保存前改了几处、改的是哪些字段、从识别到保存多久"。
- 验收：迁移只增不删且幂等(升级路径测试)；`POST /api/scan` 返回 `scanId` 且 `scan_log.duration_ms` 被写入；`POST /api/receipts` 接受可选 `meta`(路由层严格校验，非法形状 400，缺省不影响保存)；端到端：模拟扫描后改一个字段再保存，`save_events` 有 1 行且 `edited_fields` 含该字段名；**隐私测试**：表里任何列都不含商品名、金额或图片；90 天前的行在写入时被清理；`scripts/edit-diff.mjs` 只读，对空库输出"0 行"而不报错。
- 护栏：全部现有测试与端到端绿；保存接口无 `meta` 时行为不变。

**H-R1 差额行**
- 假设：`normalize()` 在税规则之后，若印出的 `total` 比 `subtotal+gst+pst` 多出超过 0.02，加一条明细 `未识别差额(请核对)`，金额 = 差额，taxable 0，分类 其他，并在 `receipt` 上标 `residual_added: true`；餐厅小票的小费会以这种形式出现在核对表里，由人改名或删除。
- 验收(离线重放 `eval/replay.cjs`，24 张首轮)：`consistent` 在餐厅组 0/3 → ≥2/3；`tipFound` 0/4 → ≥3/4(按金额匹配)；**基线里全对的小票没有一张变错**；总额已自洽的小票(costco、tnt、mix、disc 组)上**没有一条**新增差额行；全量测试绿。任一条不满足即放弃并记录。
- 护栏：`subtotal`、`total` 不改；只在 `total` 印出且大于 0 时触发。

**H-R2 日期标记**
- 假设：模型没给出合法日期时，`normalize()` 仍填今天，但 `receipt.date_guessed = true`；`ScanTab` 的日期输入框显示"日期未识别，已填今天，请核对"。
- 验收：重放里 deg-04 被标记，其余 23 张首轮结果都不被标记；端到端：模拟扫描返回无日期时提示出现，返回有日期时不出现；保存接口忽略该字段(不入库)。
- 护栏：任何数值指标不变。

**H-P1 列表去掉 raw_json**
- 假设：`listReceipts` 只选列表需要的列，每次响应体从约 240 KB 降到 ≤ 40 KB；同一份种子数据上 S1 读混合 c=50 的 p50 降 ≥20% 或吞吐升 ≥20%。
- 验收：一次性实例、同一份种子数据、同一台机器、前后各跑一次 S1(c=50，60 s)，报告两组数字与差异；详情接口仍返回 `raw_json`；前端列表没有任何字段缺失(端到端绿)。
- 护栏：不满足 20% 也可以上线(体积下降本身就是收益)，但要如实报告。

**H-P2 统计索引**
- 假设：`receipts` 上缺少 (user_id, purchased_at) / (family_id, purchased_at) 类索引，`EXPLAIN` 显示全表扫描；加索引后约 7,500 张/用户时统计接口 c=1 p50 降 ≥50%。
- 验收：`EXPLAIN` 前后对比；同一份种子数据上前后各测一次；迁移只增不删、幂等，带升级路径测试。若 `EXPLAIN` 显示已经走索引，则放弃并记录。

**H-M 模型对比**
- 假设：`gemini-2.5-flash` 在从未见过的保留集上整张全对比 flash-lite 高。
- 方法：先用 `eval/build-dataset.cjs` 的生成器用新的随机种子生成 **12 张保留集**(生成前不看、生成后不按失败调整)，再对两个模型各跑一次：已有 25 张 + 12 张保留集，共约 74 次调用；记录每次的 token 用量与耗时。
- 验收(建议规则，不改线上)：只有当保留集上 flash 的整张全对多出 ≥3 张，且每次扫描费用 ≤ flash-lite 的 2 倍，才建议切换；否则建议保持。无论结果如何，本轮不改 `.env`。
- 护栏：调用计数文件，硬上限 120(给其他实验留 30)。
