# VanSpend 压力测试报告(2026-11-11)

目标:弄清楚应用在多大负载下可用、在哪里先坏、由什么资源限制,每个数字都解释来源。
被测代码:分支 `integ/all-fixes`(`next build --webpack` 产物,`next start`)。

每个结论标注置信度: **[实测]** 直接测到;**[推断]** 由实测数字推算或排除得到;**[猜测]** 没有证据直接支持。

最重要的发现有两个:

1. **登录是全站最大的单点**。bcryptjs 是纯 JS 实现,在主线程里算(cost 10,单次约 71 ms),所以每秒只能处理约 14 次登录,而且登录进行时**所有其它请求一起被卡住**。5% 登录的混合负载(S5)吞吐只有读负载的 1/6。
2. **并发登录会触发数据库死锁**,返回 500(通用提示)。出现在 c≥20 的登录风暴和 S5 混合负载里。

## 1. 被测环境与限制

- 单台开发机(macOS,8 核,24 GB),被测 Node 进程、MySQL 容器(`vanspend-mysql-1`,MySQL 8.4.7,OrbStack/docker,无 CPU 限额,`innodb_buffer_pool_size` 128 MB,`innodb_flush_log_at_trx_commit=1`,`sync_binlog=1`)、负载生成器、以及机器上其它应用**共用这 8 核**。压测期间系统 load average 在 6–13 之间波动(其它进程),这是噪声来源。**[实测]**
- 被测是 `npx next start -p 3300`,不是线上的 standalone 容器(同一套 Next 运行时,但不是同一个进程形态);线上容器的 CPU 配额、内存、数据库位置都可能不同。**绝对数字不能直接当作线上容量,相对关系(谁先到顶、为什么)才是这份报告要说明的。**
- 数据库 `vanspend_stress`(新建,已删除),与应用同机的 docker 容器。
- 数据: 20 个用户(`stress01`–`stress20`;`stress20` 专用于锁定测试,不含小票),19 个用户各 200 张小票(共 3,800 张,15,199 条明细),由应用自己的 `POST /api/receipts` 写入。
- 不发真实 OpenRouter 请求(`OPENROUTER_API_KEY=sk-or-invalid`,扫描接口不在负载内)。
- 负载生成器同在本机,开销见第 4 节。
- 登录场景用 `X-Forwarded-For` 伪造不同来源 IP,避免被"同一 IP 失败计数"挡住;这只对本地裸跑的实例有效。线上经 Cloudflare Tunnel 时用 `CF-Connecting-IP`,不会被伪造。

### 判定规则(运行前写下)

- 膝点: 并发再增加时,吞吐增幅 < 10% 而 p99 增幅 > 2 倍的最小并发。
- 噪声底: 同一水平多次运行的吞吐差。S1 在相同数据量下 c=10/50/100/200 四次读数 1,025–1,121(±4.5%);但机器在其它进程负载较高时,同数据量下我另外测到 738 和 589(见 4.1),所以**绝对吞吐的不确定度实际约 ±25%**。延迟数字比吞吐更稳。

### 方法上的偏差(必须说明)

1. S2 写入把数据从 3,800 张小票涨到 143,515 张,之后的 S3、S4 以及第一轮 S5 是在这个大数据集上跑的。S3(bcrypt 受限)和 S4(匿名)的结果与数据量无关,保留;**S5 因此被我中止,把数据删回 3,800 张(items 15,199 条,与原来一致)后重跑**。下面 S5 的数字是重跑的。
2. 但 S3 的"c=1 读基线"和 S3 的探测路径(`/api/stats/overview`)是在大数据集上测的,所以这两列(66 ms、254 ms 等)反映的是数据量,不是登录;我另用不查库的 captcha 做探测(第 4.3 节)来排除这个混淆。顺带得到一个**[实测]**结果: 读混合 c=1 延迟在每用户约 20 → 约 7,500 张小票时从 3.8 ms 涨到 66 ms(约 17 倍),统计接口随数据量线性变慢,没有分页或汇总表。
3. S5 的写入使数据从 3,800 涨到约 7,800,所以第 4 节后续的对比诊断(S1)是在 7,800 张上做的,与第 2 节 S1 表的 3,800 张不同。
4. `S4` 的"错误率 50%"是匿名访问 `/api/auth/me` 的预期 401,不是故障;真正的错误只有 3 个连接超时(见 S4)。

## 3. 膝点分析(principle-explain-the-number)

### 3.1 读混合 S1: 为什么到 ~1,100/s 就不再增长,为什么不是 2,200/s

问题: c=10 → 200 吞吐不变(1,074 → 1,025),为什么?

- **[实测] Node 主线程被占满。** 在 S1 c=50 期间用 macOS `sample` 对 Node 进程采样 8 s(1 ms 间隔,共 6,168 个样本): 主线程在 `kevent`(空闲等待)只有 12 个样本,即约 0.2% 空闲;其余全部在 JS/事件处理(其中 `uv__stream_io` → 读到请求并执行 JS 占 5,204 个样本)。栈顶热点是 V8 的 `Scavenger`(GC,约 700 个样本)、`JsonStringifier`(JSON 序列化,231)、UTF-8 编码/解码(`WriteUtf8`/`Utf8Length`/`Utf8Decoder`,约 400)。(注: 采样本身会拖慢进程,采样期间吞吐只有 589/s,所以用它判断"忙在哪",不用它的吞吐。)
- **[实测]** `ps` 看 Node 进程 CPU 95–131%(主线程 100% + GC/辅助线程),整个读场景里不随并发变化,与"一个核被占满"一致。
- **[实测]** 响应大小: `GET /api/receipts` 每次约 240 KB(最多 200 行,`SELECT r.*` 含 `raw_json`),三个统计接口只有 49–892 字节。**[推断]** 列表接口的序列化/编码/GC 是主线程时间的主要消耗。我没有对四个接口分别压测,所以"列表占大头"是推断。
- **[推断]** 为什么 c=1 到 c=10 吞吐涨 4.6 倍而不是 10 倍: c=1 时请求耗时 3.7 ms,其中主线程约 0.9 ms(= 1/1,100),其余约 2.8 ms 在等数据库/网络,并发只需约 3.7/0.9 ≈ 4 个就能让主线程不空闲,与观察到的"c=10 已到平台"相符。
- **为什么不是翻倍(排除其它限制)**:
  - *MySQL 连接池(10)*: S1 全程 `Threads_running` 峰值 4–8,`Tconn` 恒为 13,池没有成为瓶颈(如果池是瓶颈,Node CPU 不会在 c=10 就顶满)。**[推断]**
  - *MySQL CPU*: 100–140%(8 核机器上约 1.0–1.4 核),数据库没有被占满。**[推断]**,因为 Docker 无 CPU 限额。
  - *负载生成器*: 生成器 CPU 约 58–65% 的一个核、自身事件循环延迟 p99 ≤ 8.7 ms(解析度 5 ms,所以实际接近底噪);再开第二个生成器进程(两个各 c=100,打同一个服务器)总吞吐没有增加(合计 553/s,单生成器同条件 738/s),所以**不是生成器限制**。**[实测]**
  - *单机共享*: 用第二个服务器实例做决定性对照 —— 同一个数据库上起两个 `next start`(端口 3300 与 3301),各配一个生成器各 c=50: 合计 **1,485/s**(747 + 738),对比单实例同条件 **1,137/s 与 1,139/s**(前后两次),只涨 31%,**不是翻倍**。这时 MySQL CPU 升到约 375%,机器 8 核被两个 Node(约 2.2 核)+ MySQL(约 3.8 核)+ 两个生成器(约 0.8 核)+ 其它进程基本占满。**[实测]** 结论: 一个 Node 实例的上限约 1,100–1,140/s(主线程),但再加实例时,数据库和这台 8 核机器本身先到顶,所以**这台机器上看不到比 ~1,500/s 更高的整体上限**。
- 置信度: "单实例的限制是 Node 主线程 CPU" **高**([实测]: 主线程采样 99.8% 忙、CPU 约 100%、第二生成器无增益;但两个实例并行时总量只涨 31%,说明单机上数据库与 CPU 总量会在更高负载下先成为共同限制)。

### 3.2 登录 S3: 为什么只有 ~14/s

- **[实测]** 71 ms/次,Node CPU 95–97%,MySQL 11–13%,吞吐与并发无关。**[实测]** `bcryptjs` 是纯 JS,运行在主线程;`bcryptjs` 会分片让出事件循环,所以其它请求不是被完全冻结,而是与登录交错——因此并发 20 个登录时,不查库的验证码接口 p50 265 ms、p99 1,038 ms,而空闲时是 0.4 ms。
- **[推断]** 线上容器 CPU 速度与本机不同,71 ms 这个常数会变,但"登录占满一个核、并发线性排队"的结构不会变。

### 3.3 写入 S2 与池

见 S2 小节,限制资源是 **[推断,中低置信]** "池 10 × 事务时长(刷盘)"。要确认需要改变连接池大小做对照,这超出了"不改被测源码"的约束,所以**这是本次测试中最不确定的一项**。

## 4. 排除项与补充检查

### 4.1 负载生成器本身
见 3.1。生成器 CPU 约 36–65% 的一核(S1/S4),`monitorEventLoopDelay` p99 ≤ 8.7 ms(分辨率 5 ms)。S4 在 2,800/s 时生成器 CPU 58%,没有双生成器对照(**未做**),所以 S4 的"上限由服务端决定"是 **[推断]**: c=1 时生成器用 40% CPU 打出 2,088/s,线性外推 2,800/s 约需 54%,与实测 58% 吻合,没有饱和迹象。

### 4.2 噪声
- 同一数据量、同一水平多次: S1 c=50 在 3,800 张小票时 1,121,在 7,800 张小票时前后两次 1,137 / 1,139,浸泡 936(机器同时有其它负载),双生成器对照里的单生成器 c=100 为 738,采样中 589。**同样的代码路径,吞吐在 589–1,139 之间,差别主要来自机器上其它进程(load average 6–13)和采样/双生成器的相互干扰**,所以请按 ±25% 理解绝对吞吐;排序和比例关系(读 ≈ 6× 混合,登录 ≈ 14/s)稳健,因为是同一时间窗内的对比或由机制推出。
- 登录 71 ms 的结果三次测量一致(14.2 / 14.0 / 13.7 / 14.0),这个数最稳。

### 4.3 事件循环延迟(服务端)
没有改服务端源码,所以没有直接测服务端 `monitorEventLoopDelay`。用一个并行的、约 10 次/秒的探测请求作为代理:

| 负载 | 探测路径 | 探测 p50 / p99 |
| --- | --- | --- |
| 无(c=1 空闲) | `/api/auth/me`(匿名) | 0.4 ms / 2 ms |
| S1 c=50(采样进程,吞吐受影响) | `/api/auth/captcha`(不查库) | 9 / 38 ms |
| S1 c=50(正常) | `/api/auth/me`(带 cookie,查一次库) | 约 30 / 42 ms |
| S3 登录 c=20 | `/api/auth/captcha`(不查库) | 265 / 1,038 ms |
| S4 c=200 | `/api/auth/me`(带 cookie) | 430 / 660 ms |

**[实测]** 登录场景下,不查库的路径也严重变慢,所以是事件循环(主线程)被占用,不是数据库或连接池。读场景下探测延迟不到总队列的一半,说明部分排队发生在 TCP/请求入口(Little 定律的另一部分)。

### 4.4 连接池与连接数
- 池大小 10,`queueLimit` 默认 0(无限排队,无获取超时): **[实测,读源码]**。
- 全程 `Threads_connected` 峰值 13、`SHOW PROCESSLIST` 14 行(10 个池连接 + 采样器及几个残留连接),`Max_used_connections` 23 来自压测前的种子写入,压测期间未增长。**[实测]**
- S3b 锁定风暴(2,000/s)期间池没有被占满,同时另一个用户的读请求仍能 41.6 ms(p50)返回。**[实测]**

### 4.5 5xx 与响应体
- 共 5 次 500 出现在测量窗口(S3 c=20: 3 次,S3 c=50: 1 次,S5 c=100: 1 次),服务端日志共 6 次同一个错误: `DELETE FROM login_failures WHERE username = ?` 触发 `ER_LOCK_DEADLOCK`(errno 1213)。**[实测]**
- 5 次响应体都是 `{"error":"服务器内部错误，请稍后重试"}`,不含 SQL 或堆栈;原始 SQL 只在服务端日志里。**[实测]**
- 出现率: 约 0.1–0.4%(c≥20 的登录风暴及 5% 登录的混合负载)。
- **[推断]** 原因: 不同用户名并发登录成功后各自执行 `clearLoginFailures`,同一张表的二级索引上的间隙锁与另一些请求的插入意向锁互相等待,造成死锁。`CLAUDE.md` 说"带死锁重试"的函数清单(`DEADLOCK_RETRY`)里没有登录用到的 `clearLoginFailures`,所以没有重试。这是**需要单独修的缺陷**,本次没有修。

### 4.6 5 分钟浸泡(S1 c=50,300 s)
吞吐 936/s,p50 50.1 ms,p99 99.9 ms,max 1,435 ms,0 错误;Node RSS 采样首/末 348 MB / 315 MB(中间峰值 360 MB 左右),压测结束空闲后回到 120 MB。**[实测]** 没有观察到内存增长;5 分钟只能排除快速泄漏,不能排除慢速泄漏。

### 4.7 恢复
- 每个水平之后,c=1 的基线延迟回到压测前: S1 c=1 p50 4.0 → 3.1–3.8 ms,S2 4.4 → 4.1–4.6 ms,S4 0.4 → 0.4 ms。**[实测]** 包括最重的水平(S1 c=200、S4 c=500)。S3 之后的 c=1 读基线(66 → 68–77 ms)较高,是因为当时数据集是 143k 张小票,不是恢复问题(同一数据集下前后一致)。
- S5 恢复后基线 p50 6.0 → 6.4–6.8 ms,p99 约 88–95 ms(5% 登录造成的长尾,压测前也是 96 ms)。

## 5. 局限

- 单机、同机数据库与生成器,机器上有其它负载(load average 6–13);没有在线上容器(CPU 配额、磁盘、网络)上测。
- 被测是 `next start`,不是 standalone 容器形态。
- 没有走 Cloudflare Tunnel(没有 TLS、没有边缘缓存、没有限流),也没有测带图片的写入(无 `image` 字段,不含磁盘写入和 base64 解码)。真实写入的请求体含 100 KB–数 MB 的图片,单次主线程开销会比这里的 ~1 ms 大得多,写入上限因此**会低于** 680/s。
- 没有测扫描接口(不调用 OpenRouter),所以没有包含它占用连接/内存的情况。
- 数据集每用户只有约 200 张(S1/S2),真实家庭的小票会累积;第 1 节方法偏差 2 的 143k 数据集结果显示统计接口随数据量线性变慢。
- 登录场景用伪造 `X-Forwarded-For` 绕开按 IP 计数,不能代表线上经 Tunnel 的行为。
- 没有对四个读接口分别压测,所以"列表接口占主要主线程开销"是推断。
- 没有改变连接池大小做对照,写入的限制资源判断置信度低。
- 噪声: 同一代码路径吞吐可在 589–1,139 之间波动(见 4.2),本报告每个数字应按 ±25% 看。
- 采样 `docker stats` / `docker exec` 本身会给 MySQL 增加很小的负载。
- S3b 只测了 c=20,没有测从 1,000 个不同用户名/IP 的分布式错误密码攻击(那种情况下每个用户名/IP 最多放行 10 次 bcrypt,但攻击者换名字可以持续消耗主线程 —— **[猜测]**,未测)。

## 6. 对运行方有意义的数字(不是改动建议)

- 仪表盘读取(4 个请求)按 1,100 请求/秒算约 275 次完整加载/秒;一个家庭用户的用量与这个数量级相差几个数量级,读路径在现实用户数下没有容量风险。
- 登录是真正的风险: **约 14 次/秒是全站登录的硬上限,而且一次登录风暴会让所有人同时变慢**。该限制来自 bcryptjs 在主线程里运行;换成原生 `bcrypt`(libuv 线程池)能把它移出主线程,但需要新依赖,不在本次范围。
- 登录并发死锁(4.5)是独立缺陷,建议开 issue。

## 7. 如何重跑

脚本: `scripts/loadtest.mjs`(只用 Node 内置 fetch,无依赖,不含凭据)。**只对自己启动的一次性实例使用。**

```bash
# 1) 一次性数据库(经 compose 的 MySQL,root 仅用于这个临时库)
docker exec vanspend-mysql-1 sh -c 'mysql -uroot -p"$MYSQL_ROOT_PASSWORD" -e "CREATE DATABASE IF NOT EXISTS vanspend_stress"'

# 2) 启动被测实例(无效 OpenRouter key,不会发起扫描)
set -a; . ./.env.test.local; set +a
MYSQL_HOST=127.0.0.1 MYSQL_PORT=3307 MYSQL_DATABASE=vanspend_stress \
  SESSION_SECRET=$(openssl rand -hex 24) COOKIE_SECURE=false NODE_ENV=production \
  OPENROUTER_API_KEY=sk-or-invalid PORT=3300 UPLOAD_DIR=/tmp/vs-uploads \
  npx next start -p 3300 &

# 3) 预置 20 个用户(stress01..stress20,密码自选;bcrypt 哈希用仓库的 bcryptjs 生成,
#    经 stdin 传入,不要放在命令行),直接 INSERT INTO users(...) 到 vanspend_stress
# 4) 压测
export LOAD_PASSWORD=<上一步的密码> SERVER_PID=<next-server 的 pid> \
       MYSQL_CONTAINER=vanspend-mysql-1 OUT=/tmp/results.jsonl
node scripts/loadtest.mjs seed --per 200                     # 每用户 200 张(应用自己的接口)
node scripts/loadtest.mjs run S1 --levels 10,50,100,200      # 读混合
node scripts/loadtest.mjs run S2 --levels 5,20,50            # 写入(会改变数据量!之后删回去再测读)
node scripts/loadtest.mjs run S3 --levels 5,20,50            # 登录
node scripts/loadtest.mjs run S3b --levels 20 --duration 30  # 锁定(会锁住 stress20 15 分钟)
node scripts/loadtest.mjs run S4 --levels 50,200,500         # 匿名廉价接口
node scripts/loadtest.mjs run S5 --levels 50,100             # 混合
node scripts/loadtest.mjs soak --scenario S1 --level 50 --minutes 5
```

每个水平输出一行摘要并追加一条 JSON 到 `OUT`(吞吐、按错误类别的计数与延迟、5xx 响应体、探测延迟、生成器 CPU/事件循环延迟、每 4 秒的 Node/MySQL 采样)。

注意: S2、S5 会写入小票,**之后做读测试前要把数据删回基线**(`DELETE FROM receipts WHERE id > <第 3800 个 id>`,明细级联),否则读成本会随数据量变化(本次的偏差 1)。结束后 `DROP DATABASE vanspend_stress` 并杀掉你启动的进程。
