# AGENTS.md — VanSpend

Guidance for coding agents working in this repository. Kept identical to `CLAUDE.md` below this header — when one changes, update the other.

## What this is

VanSpend is a multi-user receipt-scanning and expense-tracking app for a household in BC, Canada (Vancouver) — each household member registers their own account, and the receipts/items they upload are scoped to that account by default. Accounts can optionally belong to a **family** (a named group, unique across the system): the creator of a family can invite existing users (takes effect immediately) or approve users who apply to join (pending until the creator decides); once in the same family, members see each other's receipts and stats (read-only — deleting/editing a receipt is still owner-only). It uploads receipt photos (Costco, T&T, etc.), sends them to a multimodal LLM via OpenRouter to extract structured line-items, stores them in an external MySQL database, and charts spending/tax breakdowns (GST 5% / PST 7%) in a browser dashboard. Receipt images stay on-disk (`uploads/`); structured data lives in MySQL. Auth is session-cookie based (`iron-session`). Registration has two paths: **with an invite code** (a logged-in *normal-tier* account or an admin can generate single-use, 7-day codes; no captcha; normal scan quota) or **open** (self-hosted arithmetic image captcha, see `src/captcha.cjs`; low scan quota until an admin upgrades the account). One role beyond regular accounts: `is_admin`, bootstrapped once from `ADMIN_USERNAME`/`ADMIN_PASSWORD` in `.env`, giving access to an admin console (`/admin`) that can see/manage every user and every receipt. Users can also submit free-text feedback the admin ("作者") reviews in that console.

Frontend + API are a single Next.js (App Router) app. Business logic (DB access, OpenRouter calls) lives in framework-agnostic `.cjs` modules under `src/`, imported by the Route Handlers.

## Commands

```bash
npm install       # next + react + react-dom + react-chartjs-2 + chart.js + iron-session + mysql2 + bcryptjs (+ vitest, dev only)
cp .env.example .env   # then fill in OPENROUTER_API_KEY, MYSQL_* connection vars, SESSION_SECRET, PORT
                        # optionally ADMIN_USERNAME/ADMIN_PASSWORD to bootstrap one admin account
npm run dev        # next dev, serves http://localhost:3000 (PORT env var; Next.js reads it natively)
npm run build      # next build (Turbopack) — required before `npm start`
npm start          # next start, production mode
npm test           # vitest run — tests/**/*.test.js against a separate vanspend_test database (dropped & recreated each run)

# or via Docker:
docker compose up -d   # app + a bundled MySQL for local trial (see docker-compose.yml comments
                        # for pointing at an external MySQL instead)
```

Tests are **Vitest** (`vitest.config.js`, `tests/`); there is still no linter. `npm test` loads `.env.test` (committed, no secrets) *over* the environment, then `src/db.cjs` fills the remaining keys (MySQL user/password) from `.env`; per-machine overrides go in `.env.test.local` (gitignored). `tests/env.js` **refuses to run unless `MYSQL_DATABASE` ends in `_test`**, and `tests/globalSetup.js` drops and recreates that database before every run, so `initSchema()` builds the schema from scratch — tests never touch the real database. `tests/setup.js` points `UPLOAD_DIR` at a temp dir and replaces `next/headers` with an in-memory cookie jar (`tests/cookieJar.js`), so Route Handlers are called directly (`import * as route from '@/app/api/.../route.js'; await route.GET(req(...), ctx(params))`) with a real `iron-session` cookie written by `loginAs()` (`tests/helpers.js`). `.env.test` sets an invalid `OPENROUTER_API_KEY`, and every test that reaches `scanReceipt` must mock it (`vi.spyOn(openrouterLib, 'scanReceipt')`) — tests must never make a billed call. Every permission rule gets a positive *and* a negative test. Files run serially (`fileParallelism: false`) because they share one database.

**CI**: `.github/workflows/ci.yml` runs on every PR and on pushes to `main`: a throwaway `mysql:8.4` service (root, only inside the job), `npm ci`, `npm test`, `npm run build`, and `docker compose config` for both the default and `tunnel` profiles (it copies `.env.example` to `.env` first because compose declares `env_file: .env`). CI has no `.env`, so MySQL credentials, `SESSION_SECRET` and an invalid `OPENROUTER_API_KEY` come from the job's `env:`; `.env.test` still supplies the `vanspend_test` database name. Node 22, matching the Dockerfile.

Requires a reachable MySQL server (connection configured via `MYSQL_HOST`/`MYSQL_PORT`/`MYSQL_USER`/`MYSQL_PASSWORD`/`MYSQL_DATABASE` in `.env`) and the `MYSQL_DATABASE` schema must exist beforehand (`sql/schema.sql`, or let the app auto-create tables on startup if the account has DDL privileges).

## Module system (important, easy to get wrong)

`package.json` has `"type": "module"` — plain `.js` files are ES modules (required: Next.js App Router special files like `page.js`/`layout.js`/`route.js` must keep those exact names, so they can't be renamed to `.mjs`; the fix instead is project-wide ESM + `.cjs` for the legacy CommonJS files). Two islands of code:

- **`app/**`, `components/**`, `lib/**`, `src/session.js`, `src/http.js`** — ESM (`import`/`export`). These only ever run inside Next's bundler (Turbopack).
- **`src/db.cjs`, `src/openrouter.cjs`, `src/uploads.cjs`** — CommonJS (`require`/`module.exports`), explicit `.cjs` extension. They stay plain-`node`-`require()`-able (historically for the old `scripts/selfcheck.cjs`; now Vitest imports them the same way the app does) — Route Handlers `import` them via **default import**, e.g. `import dbApi from '@/src/db.cjs'` then `dbApi.saveReceipt(...)`, never named imports (CJS/ESM interop for named exports from a plain `module.exports = {...}` object is not reliably synthesized by Turbopack — default-import-then-property-access is the safe pattern used everywhere in this repo).
- **`@/*` path alias** (`jsconfig.json`) maps to the project root — used by every `app/api/**/route.js` file to avoid fragile relative-path counting at 3–4 levels of nesting.
- **Never use `__dirname`-relative `fs` reads in code that gets bundled by Next** (anything reachable from `app/**`). Turbopack virtualizes `__dirname` into a fake path during `next build`'s "collecting page data" step, so `fs.readFileSync(path.join(__dirname, ...))` throws `ENOENT` at build time even though it works fine under plain `node`. Use `process.cwd()` instead (real process working directory, unaffected by bundling — see `src/uploads.cjs`'s `UPLOAD_DIR` and the `.env` loaders in `src/db.cjs`/`src/openrouter.cjs`), or for static config, a plain `require('../config/config.json')` so the bundler inlines it at build time instead of reading it at runtime (see `src/openrouter.cjs`).

## Architecture

- **`app/api/**/route.js`** — one file per endpoint, each exporting `GET`/`POST`/`DELETE` etc. Thin: validate → call into `src/db.cjs`/`src/openrouter.cjs` → `NextResponse.json(...)`. Every handler wraps its body in `wrap()` (`src/http.js`) for uniform error → `{error}` 500 responses, mirroring the old Express `wrap()` middleware. Auth-gated routes start with `const { session, response } = await requireSession(); if (response) return response;` (`src/session.js`) — 401 `{error}` if not logged in. Public routes: `POST /api/auth/register|login|logout`, `GET /api/auth/me`, `GET /api/auth/captcha`, `GET /api/config`. Scanning (`POST /api/scan`) and persisting (`POST /api/receipts`) stay separate steps — the API never auto-saves an AI read.
- **`app/api/family/**/route.js`** — auth-gated (`requireSession()`) family self-service: `POST /api/family` (create, only if not already in one), `POST /api/family/apply` (request to join by name, pending), `GET /api/family/me` (own family + members +, if creator, the pending-request queue), `POST /api/family/invite` and `POST /api/family/requests/[id]` (creator-only, gated by `requireFamilyCreator()`) — invite takes effect immediately (the creator is inherently the approver), approving/rejecting a request is the only place an *apply* actually joins someone. `decideRequest()` re-checks the request's `family_id` against the caller's own family so a creator can't approve/reject another family's queue by guessing request ids.
- **`app/api/feedback/route.js`** — auth-gated: submit free-text feedback, or list *only your own* past submissions (not a public board). **`app/api/admin/feedback/route.js`** — admin-only, all users' feedback with the submitter's username.
- **`app/api/invites/**/route.js`** — auth-gated invite codes. `GET /api/invites[?kind=family|personal]` lists *only your own* codes with a derived status (`unused`/`used`/`revoked`/`expired`, plus the username that used it); `POST /api/invites` body `{ family: true }` creates a code — **strict boolean**, `"false"` is a plain code. A normal-tier account or an admin may create a plain code (**open-tier accounts get 403** — see the abuse note in Scope Boundaries); a **family code** (`invite_codes.family_id` set, registrant joins that family on signup) requires `session.familyId && session.isFamilyCreator` → else 403. Codes are 16 random bytes base64url, single-use, valid 7 days (`INVITE_VALID_DAYS`), and each user may create at most 20 codes per rolling 7 days (`INVITE_MAX_PER_WINDOW` / `INVITE_WINDOW_DAYS`) counting **every** code — used, revoked or expired too, so using or revoking one never frees a slot — enforced under `SELECT ... FOR UPDATE` on the user row → 400. `DELETE /api/invites/[id]` revokes your own unused code (404 for anyone else's, 400 if already used; revoking twice is idempotent). `[id]` segments go through `parseId()` (`src/http.js`: digits only, else 400) instead of a bare `+id`, which turned `1abc` into `NaN` bound into SQL — other pre-existing `[id]` routes still use `+id`. UI: `components/InviteCodes.js` (shared list/generate/copy-link/revoke), opened from the header as `InviteModal` (plain codes) and from `FamilyPanel` (family codes, creator only). The copied link is `/login?mode=register&code=<code>`; `app/login/page.js` reads `?code=` and `AuthGate` pre-fills it.
- **Registration (`app/api/auth/register/route.js`)** — two paths. *With `inviteCode`*: `dbApi.peekInviteCode()` pre-checks (read-only) so form validation can run before anything is created; then `dbApi.registerWithInvite()` does user insert + code consumption (+ family join for a family code) in **one transaction that first locks the code row `FOR UPDATE`**, so concurrent signups with one code yield exactly one success. No captcha. The account is `signup_source='invite'`, `scan_tier='normal'`, `invited_by=<code creator>`. A family code ignores the form's family fields; a plain code still honours them. All code-invalid reasons (unknown/used/revoked/expired/non-string) return the *same* 400 message so code state can't be probed. *Without*: captcha required, `createUser(..., { signupSource: 'open' })` → `signup_source='open'`, `scan_tier='open'`. `signupSource`/`scanTier`/`isAdmin` in the request body are always ignored.
- **Scan quota (`app/api/scan/route.js`)** — after `checkImage` and before the billed call: `dbApi.reserveScan(userId, model, limit)` inserts a `scan_log` row *first*, then counts that user's rows in the last **rolling 24 hours** (not a calendar day — avoids timezone questions) and deletes its own row + returns 429 if the count exceeds `limit` (same insert-then-count order as the login lockout, so a concurrent burst can't exceed the limit). `limit` comes from `config.scanQuota[session.scanTier]` (`open: 3`, `normal: 20`); **admins are unlimited but still logged**. `finishScan(id, success)` records the outcome; failures count too (OpenRouter bills them). Rejected requests leave no row. `scan_log.success IS NULL` = in flight (a crashed request keeps counting). `users.scan_tier` is refreshed from the DB each request (`getAuthedSession` → `session.scanTier`), so an admin upgrade applies immediately. Existing accounts migrated to `signup_source='invite'`, `scan_tier='normal'` (column defaults). Admins change a tier with `PATCH /api/admin/users/[id]` `{ tier: 'open'|'normal' }`; `listUsers()` returns `signup_source`, `scan_tier`, `inviter_username` for the admin Users tab. Note: tests must seed `scan_log` timestamps with SQL `NOW() - INTERVAL`, never JS `Date` (mysql2 serializes in the machine's timezone, MySQL in its own).
- **`app/api/admin/**/route.js`** — admin-only, gated by `requireAdmin()` (`src/session.js`, 401 if not logged in / 403 if not `session.isAdmin`) instead of `requireSession()`. Mirror the regular `receipts`/`stats` endpoints but call the *same* `src/db.cjs` functions with `scope` omitted (global, across all users) or set to `{ userId: <admin-chosen target> }` (drill-down) — see `dateFilter`'s scope note below. Plus admin-only reads: `users` (`dbApi.listUsers()`, now includes each user's `family_name`/`family_role`), `stats/by-user` (`dbApi.statsByUser()`, spend-per-user, a dimension that doesn't exist in the single-user view), `feedback` (above). `users/[id]` `DELETE` refuses to delete the currently-logged-in admin (`+id === session.userId` check) to avoid self-lockout.
- **`app/uploads/[...file]/route.js`** — replaces the old `express.static('/uploads')`. Streams a file from `UPLOAD_DIR` (`src/uploads.cjs`). **Auth-gated per receipt**: the file name must match `saveImage()`'s shape (`^[A-Za-z0-9_-]+\.(jpg|jpeg|png|webp|gif)$` — single segment, which is also the path-traversal guard), the caller must be logged in (`getAuthedSession()`), and `dbApi.findImageOwner(name)` must find a receipt whose `user_id` is the caller, whose `family_id` equals the caller's current family, or the caller is admin. Every failure (not logged in, no permission, orphan file, bad name, missing file) is the same **404** so file names can't be probed. Responses carry `Cache-Control: private, no-store` — required behind Cloudflare, which edge-caches `.jpg` etc. by default and would otherwise serve one user's receipt to anyone. Deliberately at `app/uploads/...`, not under `app/api/...`, so image URLs (`/uploads/<file>`) are unchanged; `<img>` tags send the session cookie same-origin.
- **`src/session.js`** — `iron-session` config + `getSession()` (reads/writes the encrypted session cookie via `next/headers` `cookies()`) + `getAuthedSession()` + `requireSession()`/`requireAdmin()`/`requireFamilyCreator()` (the shared 401-or-session / 401-or-403-or-session helpers used by every protected/admin/family-management route). The cookie is only trusted for **identity** (`userId`). `getAuthedSession()` — which all three `require*()` helpers and `/api/auth/me` go through — does one primary-key query per request (`dbApi.getSessionUser()`, `users LEFT JOIN families`) and overwrites `isAdmin`/`familyId`/`familyName`/`familyRole`/`accountType`/`isFamilyCreator` on the in-memory session object with the database's current values (the cookie itself is not rewritten). So revoking admin, joining a family (invited or approved) and deleting an account take effect on the very next request; a deleted account's cookie is destroyed and treated as logged out. Login/register still write those fields into the cookie, but nothing authorizes off the cached copies. Route code must keep reading permissions from the session returned by `require*()`/`getAuthedSession()`, never from a bare `getSession()` (only login/register/logout use that). `secure` comes from `COOKIE_SECURE=true` (set it for the public HTTPS deployment; leave it `false` for plain-HTTP localhost, where Safari would otherwise drop the cookie). No session table in MySQL.
- **`src/http.js`** — `wrap()` (uniform `{error}` responses; a thrown `HttpError(status, message)` keeps its status, anything else is 500), `clientIp(request)` (`CF-Connecting-IP`, else first `X-Forwarded-For`, else `null`), `readJson(request, maxBytes)` (capped streaming JSON body reader) and the `FORM_BODY_MAX` / `IMAGE_BODY_MAX` constants.
- **`src/captcha.cjs`** — registration-page human check: `generate()` picks a random single-digit `+`/`-` expression, hand-renders it as a noisy SVG (per-character random rotation/position/color + decoy lines/dots, no image library, no third-party captcha service) base64'd into a `data:image/svg+xml` URI, and signs `answer:expiresAt` with `SESSION_SECRET` (HMAC-SHA256) into an opaque token returned alongside the image — the answer is never sent as readable text/JSON, only baked into pixels. `verify(token, answer)` re-derives the signature (`crypto.timingSafeEqual`) and checks the 5-minute expiry. Stateless by design (no server-side store of open challenges); `app/api/auth/register/route.js` calls `verify()` before touching the DB.
- **`src/openrouter.cjs`** — builds the vision prompt (in Chinese, matching the product's audience) sent to the configured OpenRouter model, calls `chat/completions` with the image as a data URL, extracts/repairs JSON from the model response (`extractJson`), then `normalize()`s it: clamps categories to the configured whitelist, backfills missing `unit_price`/`subtotal`/`total` by cross-deriving from other fields, coerces `taxable` to 0/1. `normalize()` is exported and unit-tested directly by `tests/normalize.test.js` without hitting the network. Unchanged by the Next.js migration except for the `__dirname`→`require()`/`process.cwd()` fixes noted above.
- **`src/db.cjs`** — owns a `mysql2/promise` connection pool to the external MySQL database and schema (`users` 1—N `receipts` 1—N `items`, plus `families`, `family_join_requests`, `feedback`, `login_failures`, `invite_codes`, `scan_log`; cascade delete via `ON DELETE CASCADE` throughout). The pool is memoized on `globalThis.__vanspendPool` so `next dev`'s hot-reload doesn't leak a new pool (and exhaust MySQL connections) on every file save. On startup it tries to `CREATE TABLE IF NOT EXISTS` the schema, then runs upgrade-path migrations (`receipts.user_id`, `users.is_admin`, and the newer `users`/`receipts`/`items` family columns + `users.family_id`'s FK, plus the `receipts`/`items` family FKs — all checked via `information_schema` and `ALTER TABLE`d in if missing; `users`↔`families` is circular so `users.family_id`'s FK is deliberately added in its own migration step, never inline in `CREATE TABLE`, on both fresh installs and upgrades), then `seedAdmin()` (creates the `ADMIN_USERNAME`/`ADMIN_PASSWORD` account once, if set and not already present — never overwrites an existing account) — all soft-fail (warn, don't crash) if the DB account lacks DDL privileges, in which case `sql/schema.sql` must be run manually first. All queries use named-placeholder prepared statements (`namedPlaceholders: true`) — no ORM. Money/qty columns are `DECIMAL` (returned as JS numbers via `decimalNumbers: true`); `purchased_at`/timestamps are returned as strings via `dateStrings: true`. Every exported function is `async`. Stats/list functions (`overview`, `statsByCategory`, `statsBySubcategory`, `statsMonthly`, `listReceipts`, `getReceipt`, `priceTrend`, `distinctItemNames`) share a `dateFilter(from, to, scope)` helper (or an inline equivalent) that filters on `r.family_id = :familyId` if `scope.familyId` is set, else `r.user_id = :userId` if `scope.userId` is set, else no filter at all — regular routes build `scope` from the session (`familyId` if the user is in a family — so family members see each other's receipts/stats — else their own `userId`); the admin routes are the only callers that omit `scope` (global) or pass `{ userId: <target> }` (drill-down). `deleteReceipt(id, userId)` deliberately still takes a bare `userId`, never `scope` — deleting stays owner-only even inside a family (read-shared, not write-shared). `saveReceipt(receipt, items)` copies `receipt.family_id`/`family_name`/`family_role`/`account_type` onto every item row too (denormalized, so category/subcategory breakdowns can group by family without joining `users` — defaults to individual/null when the caller omits them, which is what lets tests (`tests/helpers.js` `makeReceipt`) call it with plain receipts). Family helpers: `createFamily` (name + creator, creator becomes a member in the same transaction), `findFamilyByName`/`findFamilyById`, `inviteMember` (guarded by `... AND family_id IS NULL` so it can't steal a member from another family), `applyToFamily` (de-dupes an already-pending request), `listFamilyMembers`, `listPendingRequests`, `decideRequest(requestId, familyId, approve)` (the `familyId` check is the authorization boundary — see the family API bullet above). Admin-only additions: `listUsers()` (users + aggregate receipt count/spend via `LEFT JOIN`, now also `LEFT JOIN families` for each user's family name), `deleteUser(id)`, `statsByUser(from, to)` (spend per user, `LEFT JOIN` so zero-receipt users still show up with 0). Feedback helpers: `addFeedback`, `listFeedbackByUser`, `listAllFeedback` (admin, joined with `username`). User-account helpers: `createUser(username, passwordHash, { familyRole })` (never sets `is_admin` — self-registration can't grant it), `findUserByUsername`, `countUsers`, `backfillOwnerlessReceipts`, `seedAdmin`. Request-auth helpers: `getSessionUser(id)` (per-request permission/family refresh, see `src/session.js`), `findImageOwner(imageFile)` (`/uploads` authorization, backed by the `idx_receipts_image` index — added by `migrateReceiptsImageIndex` on existing installs). Login lockout: `isLoginLocked`, `recordLoginFailure`, `countRecentLoginFailures`, `deleteLoginAttempt`, `clearLoginFailures` over the `login_failures` table (no FK — it stores whatever username was typed, existing or not).
- **`sql/schema.sql`** — standalone MySQL DDL (`CREATE DATABASE` + `users`/`families`/`family_join_requests`/`receipts`/`items`/`feedback`/`login_failures`/`invite_codes`/`scan_log` tables), kept in sync by hand with the DDL embedded in `src/db.cjs`.
- **`config/config.json`** — single source of truth for the model slug, tax rates, and the category whitelist. Changing `categories` here changes both the AI prompt (`src/openrouter.cjs`) and the frontend `<select>` options simultaneously. `model` can be overridden per-deployment via `OPENROUTER_MODEL` in `.env`. `scanQuota` (`{ open: 3, normal: 20 }`) is the per-user scan limit per rolling 24 h by `users.scan_tier`. **`port` is no longer read** — Next.js reads the `PORT` env var natively instead (set it in `.env`/compose, default `3000`).
- **`app/page.js`** (client component) — checks `GET /api/auth/me` on load; renders `components/landing/Landing.js` (the public marketing page) if unauthenticated, else `Header` + the tab shell (scan / dashboard / list / family). `Header` is deliberately *inside* the logged-in branch — an anonymous visitor must not see its `.env` "Key 未配置" badge — and `/api/config` is only fetched once logged in for the same reason. All four tab components stay mounted at all times (visibility toggled via the `.hide` CSS class, not conditional unmounting) so switching tabs doesn't reset in-progress state (e.g. the scan tab's editable table) — this matches the original vanilla-JS app's DOM-toggling behavior. Passes `showOwner={!!user.familyId}` to `ReceiptsTab` so the owner-username column only appears once there's actually more than one possible owner. `components/Header.js` shows a "管理后台" link to `/admin` when `user.isAdmin`, plus "修改密码"/"意见反馈" modal triggers for everyone.
- **`app/admin/page.js`** (client component) — same auth-check shape as `app/page.js`, but checks `isAdmin` from `/api/auth/me` and shows a plain "no permission" card (not the login gate) if the logged-in user isn't an admin. Four tabs, same always-mounted/`.hide` pattern: `components/admin/StatsPanel.js` (KPIs + category/subcategory/monthly charts, all with an optional user-scope dropdown, plus a `stats/by-user` bar chart that doesn't exist in the regular dashboard), `components/admin/ReceiptsPanel.js` (structurally `ReceiptsTab` + an owner-username column + a user filter dropdown, hitting `/api/admin/receipts*`), `components/admin/UsersPanel.js` (user list + family name/role columns + delete), `components/admin/FeedbackPanel.js` (read-only list of every user's feedback + who sent it).
- **`components/FamilyPanel.js`** — the "家庭" tab. No family yet → two small forms (create with a unique name / apply to join an existing name). In a family → family name, own role, member table, and — creator-only — an invite-by-username form and a pending-requests table with 通过/拒绝 buttons. Re-`GET /api/family/me` after every mutation rather than patching local state.
- **`components/FeedbackModal.js`** — user-facing submit-plus-own-history modal opened from `Header`.
- **`components/ScanTab.js` / `DashboardTab.js` / `ReceiptsTab.js`** — direct structural ports of the three original `<section>`s. `DashboardTab` renders Chart.js via `react-chartjs-2` (`Doughnut`/`Bar`/`Line`) instead of imperative `new Chart(...)` calls; same series colors/options (already CVD/contrast-checked, see `dataviz` skill), same 4 charts (category doughnut, subcategory bar, monthly stacked bar, price-trend line).
- **`lib/api.js`** — client-side `api()` fetch wrapper (mirrors the old page-scoped `api()`); on a 401 response it calls a registered "unauthorized" callback (set by `app/page.js`) that bounces the UI back to the landing page, so an expired session anywhere in the app recovers gracefully instead of showing a raw error. **`/api/auth/*` is exempt from that callback** — a 401 there means "this form was filled in wrong" (wrong password on login, wrong *current* password on `/api/auth/password`, or the normal logged-out probe on `/api/auth/me`), not "session expired"; without the exemption a password typo would eject a logged-in user. `setUnauthorizedHandler()` returns a disposer so the registering effect can clean up.
- **`components/landing/`** — the public marketing page shown at `/` when logged out. `Landing.js` (shell: language + variant state, nav, footer, reveal observer), `sections.js` (the content sections, all `({t, tone, variant}) => markup`), `mocks.js` (pure-CSS product mockups — phone with animated scan bar, receipt card, family ledger, bar chart, donut; all illustrative sample data, each flagged with a 示例/Sample badge), `copy.js` (the **only** place landing text lives, zh + en with identical keys), `useReveal.js` (one IntersectionObserver for the page), `VariantSwitch.js` (temporary A/B control, carries its own deletion checklist), `landing.css` (all `.lp`/`.lp-auth` styles). **Two design variants** (1a 产品先行 / 1b 价值先行) differ *only* in section order and per-section tone — both are driven by the `ORDER` table in `Landing.js`, so no copy or component is duplicated; pick one and delete the loser per `VariantSwitch.js`'s comment.
- **`app/login/page.js`** — server component, reads `?mode=register` from `searchParams` (a page prop, so no `useSearchParams`/Suspense needed) and hands it to `components/LoginClient.js`, which renders the *unmodified* `AuthGate` on a light card and navigates with `router.replace('/')` on success. It handles the `pendingFamilyRequest` case inline rather than via `showToast` — `lib/toast.js` has no buffering, so a toast fired immediately before navigating is lost.
- **Landing/login CSS isolation (easy to get wrong)** — `app/globals.css` is a hardcoded dark theme with bare element selectors (`button`, `input`, `select`, `a`, `table`, `header`) that leak into any page. `landing.css` therefore prefixes every rule with `.lp` or `.lp-auth`. Three rules to preserve: (1) don't use `<header>` or `<table>` inside `.lp`; (2) never nest `.lp` and `.lp-auth` — their button resets have equal specificity and would tie on source order; (3) the element reset inside `.lp` uses `:where()` so its specificity is 0, otherwise it outranks the layout classes' own `margin-top` and every section collapses together. `.lp-auth` re-themes the login form purely by **rebinding** the CSS variables `globals.css` already uses (`--card`, `--line`, `--txt`, `--mut`, `--acc`, …) — if someone later hardcodes a color into those `globals.css` rules, `/login` breaks silently.
- **`lib/toast.js`** / **`components/Toast.js`** — small pub-sub replacing the old global `toast()` function + `#toast` div.
- **`lib/dateRange.js`** — the shared date-preset helpers (当月/上月/近3个月/近半年/近1年) used by both `DashboardTab` and `ReceiptsTab`.
- **`app/globals.css`** — the original `<style>` block ported verbatim (same CSS vars, dark theme, chart-series colors) — no visual redesign, no CSS framework.
- **`tests/`** — the Vitest suite described under Commands: `normalize`/stats (migrated from the deleted `scripts/selfcheck.cjs`), session freshness, `/uploads` authorization, login lockout, upload size limit, body limits, invite codes (`invites`, `register`), scan quota (`quota`), admin tier/list (`admin-tier`), and the `users` upgrade migration (`migration` — it drops the new columns from the test DB's `users` and runs `migrateUsersInviteColumns` again, and the migration itself restores them, so later files still see the full schema; only the column order in `users` changes).
- **`docker-compose.yml`** — `app` publishes only on `127.0.0.1:${PORT}` (never `0.0.0.0`): public traffic must come through the `cloudflared` service (Cloudflare Tunnel, `profiles: ["tunnel"]`, started with `docker compose --profile tunnel up -d`, `TUNNEL_TOKEN` from `.env`; the Tunnel's public hostname points at `http://app:3000`). That loopback-only binding is what makes `CF-Connecting-IP` trustworthy. The bundled `mysql` service publishes no ports.
- **`Dockerfile`** — multi-stage (`deps` → `builder` runs `next build` → `runner`), using Next's `output: 'standalone'` (`next.config.js`) so the final image only ships the traced dependency graph, not the whole `node_modules`. `config/` and `sql/` are copied explicitly into the runner stage since they're read via `fs`/`require` at runtime, not part of the traced JS import graph the standalone build follows for everything. Still Alpine, still a non-root user, still `EXPOSE 3000`.

### Data flow for a receipt

1. Frontend posts the image as a base64 data URL to `POST /api/scan` → `openrouterLib.scanReceipt()` → normalized `{receipt, items, raw}`, **not yet persisted**.
2. User reviews/edits the extracted line items in the editable table (`ScanTab`) — AI misreads are expected and must be caught here, there is no offline OCR fallback.
3. Frontend posts the (possibly edited) `{receipt, items, image}` to `POST /api/receipts` → image is base64-decoded to a file in `uploads/` (`saveImage()`, `src/uploads.cjs`); the route handler stamps the current `family_id`/`family_name`/`family_role`/`account_type` from the session onto the receipt object, then `dbApi.saveReceipt()` inserts receipt + items (family fields copied onto every item too) in one transaction.
4. `DashboardTab` reads aggregates from the `/api/stats/*` endpoints, all of which accept optional `from`/`to` date-range query params and are scoped to the family if the caller is in one, else to just that caller.

### Domain-specific rules to preserve

- GST/PST splitting follows BC-specific tax rules (5%/7%); when a receipt only prints a combined tax line, the app estimates the 5/7 split rather than guessing — this logic lives in the AI prompt (`openrouter.cjs:buildPrompt`), not in code.
- `name_norm` (AI-normalized item name) is what powers cross-time price trend matching (`priceTrend`, a `LIKE '%name%'` substring match on `name_norm`/`name_raw`) — it's inherently fuzzy since it's model-generated, not a canonical SKU.
- API error shape is always `{ error: string }` with a matching status: 400 bad input, 401 not logged in, 403 not admin / not family creator, 404 not found *or* not allowed to see it (`/uploads`), 413 body/image too large, 429 login locked, 500 thrown errors. `wrap()` turns a thrown `HttpError(status, message)` (`src/http.js`) into that status and anything else into 500. Read request bodies with `readJson(request, maxBytes)` (`src/http.js`, streams with a hard cap → 413, bad JSON → 400; `FORM_BODY_MAX` 16 KB for forms, `IMAGE_BODY_MAX` 16 MB for image routes) rather than bare `request.json()` — used by **every** route that reads a JSON body (any other route should do the same); valid JSON that isn't an object (`null`, arrays, numbers) is also a 400.

## Scope Boundaries

**Known trade-offs and risks**
- AI extraction is not 100% accurate; the manual review/edit step before save is a required control, not optional UX polish.
- Tax split (GST/PST) is estimated by ratio when a receipt only prints one combined tax total.
- Cross-time price comparison relies on fuzzy `name_norm` matching.
- Every scan costs an OpenRouter API call (billed, though cheap with the default Gemini 2.5 Flash model).
- Session cookie is signed/encrypted but stateless (`iron-session`) — no server-side way to force-invalidate one *specific* session before its cookie expires (no "log out all devices"; changing the password doesn't log out other devices). Permissions and family membership are re-read from MySQL on every request (one extra primary-key query per request), so they no longer lag; deleting the account is the only way to kill all of a user's sessions at once.
- Login lockout (`app/api/auth/login/route.js`): 10 failures within 15 minutes for the same username **or** the same IP lock that key for a **fixed 15 minutes from the 10th failure** (429, even with the right password). `dbApi.isLoginLocked` finds the key's latest failure L inside the window and counts failures in (L−15 min, L]; locked requests write nothing, so L doesn't move and the lock lasts exactly 15 minutes. **Order matters (race fix):** the route checks the lock, then *records the attempt first* (`recordLoginFailure` returns its id), then counts (`countRecentLoginFailures`), and only if the count is ≤ 10 runs bcrypt — otherwise it deletes its own row (`deleteLoginAttempt`) and returns 429. Counting before recording would let a concurrent burst all read 0 and each get a guess. A failed password keeps the row; success clears that username's rows (`clearLoginFailures`), not the IP's. Rows live in `login_failures` (pruned after a day on each insert; username/IP truncated to the column widths 100/64 so oversized input can't 500). IP comes from `clientIp()` (`src/http.js`): `CF-Connecting-IP`, else the first `X-Forwarded-For` entry (Route Handlers can't see the socket address; Next only fills XFF from the socket when the client didn't send one, so this fallback is client-spoofable and is only reached when the request didn't come through the Tunnel), else `null` → the IP dimension is skipped for that request rather than lumping everyone into one bucket. In local dev every request usually shares `::1`, so 10 failures lock the whole machine out for 15 minutes. Anyone can deliberately lock a known username (including the admin) for 15 minutes. `/api/auth/password` (current-password check) is not rate-limited.
- Images: `uploadsLib.checkImage(image)` (`src/uploads.cjs`) rejects anything that isn't a string `data:image/(png|jpeg|jpg|webp|gif);base64,...` with 400 (so `data:image/html` or `svg+xml` can't be written to disk) (an array-wrapped image used to pass the size check as 0 bytes while `saveImage`'s regex still matched it) and a decoded size over 10 MB with 413. `/api/scan` and `/api/receipts` call it before the billed OpenRouter call / before writing to disk, and `saveImage()` independently refuses non-strings and oversized input. `ScanTab` re-encodes images whose long edge exceeds 2000 px to JPEG (quality 0.85) in the browser first; formats the browser can't decode (e.g. HEIC in some browsers) are uploaded as-is.
- `next build` meaningfully increases Docker image size/build time versus a zero-build static-file image.
- The admin console can view/delete any user's receipts and delete any user account (cascades their data) — real destructive cross-user power, no undo, no audit log of who did what.
- Joining a family (invite or approved apply) grants read access to every other member's receipts/items/stats — a member who shouldn't see someone else's spending has no finer-grained opt-out short of leaving the family (which isn't built — see below).
- The registration-page captcha is a self-hosted, low-cost deterrent (a single-digit arithmetic problem rendered as a noisy SVG), not a hardened anti-bot service — it raises the bar over a bare form but won't stop a determined/targeted attacker the way a commercial captcha service would. Its SVG also bakes in a dark background (`src/captcha.cjs`), which now shows as a dark slab on the light `/login` card.
- Two visual languages coexist: the marketing landing page and `/login` are light (Apple-ish, `landing.css`), the logged-in app is dark (`globals.css`). Logging in is a deliberate one-time jolt between them, not an oversight.
- The landing page's charts/ledger/amounts are hardcoded illustrative mockups (badged 示例/Sample), not live data. Its copy is written to match what the app actually does — including saying out loud that scanning sends the image to OpenRouter. **Don't add a marketing claim without checking the code supports it**; the source design doc promised on-device photos, E2E encryption, CSV export, self-learning categories and a 6-member cap, none of which exist.
- The landing page and register form must stay truthful about the two registration paths (invite code vs. open with a lower daily scan limit); the landing copy is rewritten in P5.
- **Invite-code abuse model (decided after verification found an amplification hole).** Invite signup skips the captcha and grants the normal quota, so if *any* account could mint codes, one captcha solve would roll out unlimited captcha-free normal accounts (20 per account per generation). Mitigations in place: accounts on the `open` tier cannot mint codes (admins can; an admin must upgrade a user first), and every account is capped at 20 codes per rolling 7 days counting used ones. What remains is a **trust chain**: a normal-tier account that goes rogue can still recruit ~20 accounts a week, and each of those can recruit 20 more. The admin Users tab shows who invited whom (`inviter_username`) and can downgrade an account to `open`, which stops its minting but does not revoke codes it already issued. No IP-based registration limit, no account-age gate. A valid code can also probe whether a username exists (a taken username returns 400 without burning the code) — the open path allows the same, one captcha per probe.
- Concurrent scans fail closed: `reserveScan` inserts before counting, so several simultaneous scans can all see each other's pending rows and be rejected even though the user is under quota (never over). A rejected scan leaves no row and costs nothing.
- Both landing variants (1a/1b) and both languages ship at once, so there are two heroes and two copy sets to keep in sync until one variant is deleted.

**Strict constraints**
- Requires a reachable external MySQL server; `MYSQL_*` credentials live in `.env` (never commit real credentials).
- Being taken public via Cloudflare Tunnel (GitHub issue #1, phases P0–P5). P0's hardening is in place (per-request session check, `/uploads` authorization, login lockout, upload limits, Tunnel + `COOKIE_SECURE`); the rest of the trust-model text in this file is rewritten in P5. Until then: never publish the app port or MySQL beyond loopback/the compose network — the MySQL server must not be reachable from the internet, and `COOKIE_SECURE=true` is mandatory on the public deployment.
- Receipt images (`uploads/`) remain local disk files, not stored in MySQL. `/uploads` is authorized per receipt (owner / same family / admin, else 404) — see the `app/uploads` bullet above.
- Registration is open: either by invite code (any logged-in user may generate codes, no approval) or without one (captcha-guarded, low daily scan quota, no approval — an admin can raise the quota). Exactly one elevated role (`is_admin` boolean, no finer-grained permissions), grantable only via the `ADMIN_USERNAME`/`ADMIN_PASSWORD` bootstrap — never through the registration API. Joining a *family* is the one place something does require approval: an apply request sits pending until the family's creator (and only the creator — not just any member) approves or rejects it; an invite from the creator, by contrast, takes effect immediately.
- A family's creator is fixed at creation time — no transferring creatorship, no promoting another member, no deleting a family, no removing/kicking a member, no self-service "leave family". The only way out of a family right now is an admin deleting the user account outright.
- Plain JS/JSX, no TypeScript, no ESLint config, no state-management library, no CSS framework. No i18n library either — the landing page's bilingual copy is a plain `{zh, en}` object in `components/landing/copy.js`, and only the landing page is bilingual (the login form, the app and `/admin` stay Chinese).
- No static asset directory: there is no `public/`, and the Dockerfile only copies `.next/standalone`, `.next/static`, `config/` and `sql/`. Every landing visual must stay pure CSS / inline SVG / emoji — an image or webfont would 404 in the Docker image.

**Explicitly not included**
- No editing receipts/line-items from the admin console (view + delete only — the regular user flow doesn't support post-save editing either).
- No audit log of admin actions, no "log in as" / impersonation flow.
- No in-app admin creation/promotion UI or self-service admin password change.
- No password reset or email verification.
- No pricing/paid tiers anywhere (deliberately dropped from the source design), no server-rendered or crawlable landing page (`/` still renders nothing until the client's `/api/auth/me` resolves), no OG/SEO metadata, no `/en` route, and no redirect away from `/login` for an already-logged-in visitor.
- No cloud backup/sync of `uploads/`.
- No budgets/alerts, no income tracking, no PDF/Excel export.
- No batch receipt import or bank/credit-card statement reconciliation.
- No offline OCR fallback.
- No server-side rendering/data-fetching optimizations — everything stays client-rendered (`"use client"`), same as the original SPA.
- No connection-pool tuning, retry/backoff, or migration framework beyond `schema.sql` + the app's own `CREATE TABLE IF NOT EXISTS` / column-backfill migrations.
- No family management beyond invite/apply/approve/reject: no removing a member, no leaving, no transferring/renaming, no deleting a family, no admin UI for any of that (admin can only delete the underlying user account).
- No write-sharing inside a family — editing or deleting a receipt is always owner-only, regardless of family membership.
- No email/push notification when invited, applied-to, approved, or rejected — the invitee/applicant only finds out by checking the "家庭" tab (or, for an invite, by the fact that their next page load now shows a family — session permissions are re-read from the DB on every request).
- No reply/status/resolution workflow on feedback — it's a one-way box (user writes, admin reads); no threading, no marking resolved, no notifying the submitter back.
- No image-based (photo) captcha, no third-party captcha service (reCAPTCHA/Turnstile/hCaptcha) — see the self-hosted-SVG trade-off above.
