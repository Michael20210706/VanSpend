# AGENTS.md — VanSpend

Guidance for coding agents working in this repository. Kept identical to `CLAUDE.md` below this header — when one changes, update the other.

## What this is

VanSpend is a multi-user receipt-scanning and expense-tracking app for a household in BC, Canada (Vancouver) — each household member registers their own account, and the receipts/items they upload are scoped to that account by default. Accounts can optionally belong to a **family** (a named group, unique across the system): the creator of a family can invite existing users (takes effect immediately) or approve users who apply to join (pending until the creator decides); once in the same family, members see each other's receipts and stats (read-only — deleting/editing a receipt is still owner-only). It uploads receipt photos (Costco, T&T, etc.), sends them to a multimodal LLM via OpenRouter to extract structured line-items, stores them in an external MySQL database, and charts spending/tax breakdowns (GST 5% / PST 7%) in a browser dashboard. Receipt images stay on-disk (`uploads/`); structured data lives in MySQL. Auth is session-cookie based (`iron-session`). Registration has two paths: **with an invite code** (a logged-in *normal-tier* account or an admin can generate single-use, 7-day codes; no captcha; normal scan quota) or **open** (self-hosted arithmetic image captcha, see `src/captcha.cjs`; low scan quota until an admin upgrades the account). One role beyond regular accounts: `is_admin`, bootstrapped once from `ADMIN_USERNAME`/`ADMIN_PASSWORD` in `.env`, giving access to an admin console (`/admin`) that can see/manage every user and every receipt. Users can also submit free-text feedback the admin ("作者") reviews in that console. **It is deployed on the public internet** (Cloudflare Tunnel, see *Trust model* below), so every endpoint must be treated as reachable by anonymous strangers, not only by household members on a LAN.

Frontend + API are a single Next.js (App Router) app. Business logic (DB access, OpenRouter calls) lives in framework-agnostic `.cjs` modules under `src/`, imported by the Route Handlers.

## Commands

```bash
npm install       # next + react + react-dom + react-chartjs-2 + chart.js + iron-session + mysql2 + bcryptjs (+ vitest, dev only)
cp .env.example .env   # then fill in OPENROUTER_API_KEY, MYSQL_* connection vars, SESSION_SECRET, PORT
                        # optionally ADMIN_USERNAME/ADMIN_PASSWORD to bootstrap one admin account
npm run dev        # next dev, serves http://localhost:3000 (PORT env var; Next.js reads it natively)
npm run build      # next build (Turbopack) — required before `npm start`
npm start          # next start, production mode
npm test           # vitest run — tests/**/*.test.js against a separate vanspend_test database (dropped & recreated each run)

# or via Docker:
docker compose up -d   # app + a bundled MySQL for local trial (see docker-compose.yml comments
                        # for pointing at an external MySQL instead)
```

Tests are **Vitest** (`vitest.config.js`, `tests/`); there is still no linter. `npm test` loads `.env.test` (committed, no secrets) *over* the environment, then `src/db.cjs` fills the remaining keys (MySQL user/password) from `.env`; per-machine overrides go in `.env.test.local` (gitignored). `tests/env.js` **refuses to run unless `MYSQL_DATABASE` ends in `_test`**, and `tests/globalSetup.js` drops and recreates that database before every run, so `initSchema()` builds the schema from scratch — tests never touch the real database. `tests/setup.js` points `UPLOAD_DIR` at a temp dir and replaces `next/headers` with an in-memory cookie jar (`tests/cookieJar.js`), so Route Handlers are called directly (`import * as route from '@/app/api/.../route.js'; await route.GET(req(...), ctx(params))`) with a real `iron-session` cookie written by `loginAs()` (`tests/helpers.js`). `.env.test` sets an invalid `OPENROUTER_API_KEY`, and every test that reaches `scanReceipt` must mock it (`vi.spyOn(openrouterLib, 'scanReceipt')`) — tests must never make a billed call. Every permission rule gets a positive *and* a negative test. Files run serially (`fileParallelism: false`) because they share one database.

**CI**: `.github/workflows/ci.yml` runs on every PR and on pushes to `main`: a throwaway `mysql:8.4` service (root, only inside the job), `npm ci`, `npm test`, `npm run build`, and `docker compose config` for both the default and `tunnel` profiles (it copies `.env.example` to `.env` first because compose declares `env_file: .env`). CI has no `.env`, so MySQL credentials, `SESSION_SECRET` and an invalid `OPENROUTER_API_KEY` come from the job's `env:`; `.env.test` still supplies the `vanspend_test` database name. Node 22, matching the Dockerfile.

Requires a reachable MySQL server (connection configured via `MYSQL_HOST`/`MYSQL_PORT`/`MYSQL_USER`/`MYSQL_PASSWORD`/`MYSQL_DATABASE` in `.env`) and the `MYSQL_DATABASE` schema must exist beforehand (`sql/schema.sql`, or let the app auto-create tables on startup if the account has DDL privileges).

## Module system (important, easy to get wrong)

`package.json` has `"type": "module"` — plain `.js` files are ES modules (required: Next.js App Router special files like `page.js`/`layout.js`/`route.js` must keep those exact names, so they can't be renamed to `.mjs`; the fix instead is project-wide ESM + `.cjs` for the legacy CommonJS files). Two islands of code:

- **`app/**`, `components/**`, `lib/**`, `src/session.js`, `src/http.js`** — ESM (`import`/`export`). These only ever run inside Next's bundler (Turbopack).
- **`src/db.cjs`, `src/openrouter.cjs`, `src/uploads.cjs`** — CommonJS (`require`/`module.exports`), explicit `.cjs` extension. They stay plain-`node`-`require()`-able (historically for the old `scripts/selfcheck.cjs`; now Vitest imports them the same way the app does) — Route Handlers `import` them via **default import**, e.g. `import dbApi from '@/src/db.cjs'` then `dbApi.saveReceipt(...)`, never named imports (CJS/ESM interop for named exports from a plain `module.exports = {...}` object is not reliably synthesized by Turbopack — default-import-then-property-access is the safe pattern used everywhere in this repo).
- **`@/*` path alias** (`jsconfig.json`) maps to the project root — used by every `app/api/**/route.js` file to avoid fragile relative-path counting at 3–4 levels of nesting.
- **Never use `__dirname`-relative `fs` reads in code that gets bundled by Next** (anything reachable from `app/**`). Turbopack virtualizes `__dirname` into a fake path during `next build`'s "collecting page data" step, so `fs.readFileSync(path.join(__dirname, ...))` throws `ENOENT` at build time even though it works fine under plain `node`. Use `process.cwd()` instead (real process working directory, unaffected by bundling — see `src/uploads.cjs`'s `UPLOAD_DIR` and the `.env` loaders in `src/db.cjs`/`src/openrouter.cjs`), or for static config, a plain `require('../config/config.json')` so the bundler inlines it at build time instead of reading it at runtime (see `src/openrouter.cjs`).

## Architecture

- **`app/api/**/route.js`** — one file per endpoint, each exporting `GET`/`POST`/`DELETE` etc. Thin: validate → call into `src/db.cjs`/`src/openrouter.cjs` → `NextResponse.json(...)`. Every handler wraps its body in `wrap()` (`src/http.js`) for uniform error → `{error}` 500 responses, mirroring the old Express `wrap()` middleware. Auth-gated routes start with `const { session, response } = await requireSession(); if (response) return response;` (`src/session.js`) — 401 `{error}` if not logged in. Public routes: `POST /api/auth/register|login|logout`, `GET /api/auth/me`, `GET /api/auth/captcha` (`GET /api/config` is login-only since P5). Scanning (`POST /api/scan`) and persisting (`POST /api/receipts`) stay separate steps — the API never auto-saves an AI read.
- **Account operations (P4)** — three things, all in `src/db.cjs` + thin routes.
  - *Admin password reset*: `POST /api/admin/users/[id]/reset-password` (`requireAdmin`). The server generates a 12-char random temporary password (`crypto.randomInt`, no look-alike characters), stores only its bcrypt hash, sets `users.must_change_password = 1` and returns the temporary password **once** in the response (`Cache-Control: no-store`) — the admin has to pass it on; it is never stored in plaintext and never written to the audit log. Refused (400) for oneself (use "change password") and for admin accounts (their password comes from the `.env` bootstrap); 404 for an unknown user. `dbApi.resetUserPassword()` does it in one transaction with the audit row.
  - *Must change password*: while `must_change_password` is set, **every** `requireSession()`/`requireAdmin()`/`requireFamilyCreator()` call returns `403 { error, code: 'password_change_required' }`, and `/uploads` returns 404 — except `/api/auth/me` (returns `mustChangePassword`), `/api/auth/logout`, and `/api/auth/password`, which opts in with `requireSession({ allowPasswordChange: true })`. The flag is read from the DB on every request like the rest of the session (`getSessionUser`), so devices that were already logged in are blocked too even though sessions are stateless. `POST /api/auth/password` clears it (`updatePassword` sets it to 0) and now also rejects a new password equal to the current one (400). UI: `app/page.js` renders only a non-dismissable `ChangePasswordModal forced` (plus a logout link) while `user.mustChangePassword`. Resetting does not invalidate other sessions' cookies — it just locks them behind the password change.
  - *Self-service account deletion*: `POST /api/auth/delete-account` `{ password }` (under `/api/auth/` so the wrong-password 401 doesn't bounce the UI to the landing page). Order: session (403 if must-change) → password present (400) → admin accounts refused (403) → bcrypt check (401) → `dbApi.deleteOwnAccount()`: reads the user's `family_id`, then in a transaction **locks the family row first, then the user row** (retrying if the family changed while waiting — same order as every family operation, so no deadlock with leave/remove/transfer/dissolve; a test races them), refuses with 400 if the user is a family **creator** (they must transfer or dissolve first — we don't decide that for them; this includes a creator who is the only member), otherwise deletes the user row (receipts/items/join requests/invite codes cascade through FKs). The receipts' image file names are read in the same transaction and the files are deleted **after commit** by `uploadsLib.deleteImages()` (name-shape checked; a missing file is not an error). Then the session is destroyed. The password check on this endpoint is not rate-limited, same as `/api/auth/password`. UI: `components/DeleteAccountModal.js`, opened from the header's 注销账号 link (hidden for admins). The admin's `DELETE /api/admin/users/[id]` now removes the deleted user's image files the same way (`dbApi.deleteUserFull()` returns `{ deleted, images }`; `deleteUser()` still returns the count).
  - *Admin audit log*: table `admin_audit_log` (`admin_id` FK `ON DELETE SET NULL`, plus text snapshots `admin_username`, `target_label`, `detail` so a row stays readable after the target or the admin is deleted). Rows are written **inside the same transaction as the action** by `insertAudit()` for exactly four admin writes: `delete_user` (`deleteUserFull`, detail = number of receipts removed and families dissolved), `delete_receipt` (`adminDeleteReceipt`: store/date/total snapshot + owner), `reset_password` (`resetUserPassword`), `set_tier` (`setScanTier`, detail = old → new tier). Nothing is logged when nothing was written (unknown id, refused request, non-admin caller) and **views are never logged**. A user's own self-deletion is not an admin action and is not logged. Read-only: `GET /api/admin/audit[?limit=]` (admin only, newest first, default 200, max 500); the route exports only `GET` and nothing else in the app updates or deletes these rows. UI: `components/admin/AuditPanel.js` (the admin page's 操作日志 tab). No retention/pruning, no export. Deleting a *single* receipt (own or admin) still leaves its image file on disk, as before — only account deletion removes images.
- **Receipt editing and duplicate hint (P3)** — `PUT /api/receipts/[id]` edits a saved receipt: **owner only** (same permission as delete — not family members, not the family creator, not admins; anything not yours is 404). Body `{ receipt: { store, purchased_at, gst, pst }, items: [...] }`, read with `EDIT_BODY_MAX` (256 KB, `src/http.js`). Validation is strict and lives in `src/receiptInput.cjs` `validateEdit()` — unlike `normalize()` (which silently repairs AI output) an invalid user edit is a 400: non-empty store ≤255 (no NUL characters), real `YYYY-MM-DD` date with year ≥ 1000, numeric GST/PST/qty/amount (must be JS numbers, within the DECIMAL column ranges), `qty` either 0 or at least 0.001 in magnitude (the column keeps 3 decimals; a smaller qty would be stored as 0 and blow up the derived unit price), `taxable` boolean/0/1, 1–300 items, field length caps; negative amounts are allowed (discount lines). Item amounts, GST and PST are rounded to cents *before* summing, so the stored subtotal/total always equal the sum of the stored rows; a back-derived `unit_price` (amount ÷ qty when the unit price is blank) that would overflow `DECIMAL(10,4)` is a 400, not a database 500. It then runs the result through `normalize()` with `subtotal`/`total` forced to 0, so **the server recomputes `subtotal` = sum of item amounts and `total` = subtotal + GST + PST; any `subtotal`/`total` in the request is ignored** (categories outside the whitelist become `其他`, a missing `unit_price` is back-derived). `dbApi.updateReceipt()` takes the locks in the same order as every family operation — it reads the receipt's `family_id`, then in the transaction takes the **`families` row `FOR SHARE` first**, then the receipt row `FOR UPDATE` (retrying if `family_id` changed while waiting), then items. (Locking the receipt first deadlocked with rename/dissolve, because inserting an item with a `family_id` needs a shared lock on the `families` row through the FK; a regression test races edits against rename and dissolve.) It updates only `store/purchased_at/subtotal/gst/pst/total`, deletes and re-inserts the items stamping them with the receipt's *current* `family_*` values; `image_file`, `raw_json`, `currency` and the receipt's family fields are never touched. `GET /api/receipts/duplicates?store=&date=&total=` (auth-gated; `date` must be a real date, else 400) returns up to 5 receipts in the caller's `memberScope()` with the same trimmed, case-insensitive store + same date + same total — **a hint only**: `POST /api/receipts` never refuses a duplicate. `ScanTab` calls it before saving and shows a `confirm()`; a failed lookup never blocks the save. A member's pre-join personal receipts are not matched for other members (same scope rule as everything else). UI: `components/ItemsEditor.js` (item table shared by `ScanTab` and the editor), `components/ReceiptEditor.js` (opened from the receipt detail card's 编辑 button, shown only when `detail.user_id` is the caller; subtotal/total are a live preview of the server rule).
- **`app/api/family/**/route.js`** — auth-gated (`requireSession()`) family self-service: `POST /api/family` (create, only if not already in one), `POST /api/family/apply` (request to join by name, pending), `GET /api/family/me` (own family + members +, if creator, the pending-request queue), `POST /api/family/invite` and `POST /api/family/requests/[id]` (creator-only, gated by `requireFamilyCreator()`) — invite takes effect immediately (the creator is inherently the approver), approving/rejecting a request is the only place an *apply* actually joins someone. `decideRequest()` re-checks the request's `family_id` against the caller's own family so a creator can't approve/reject another family's queue by guessing request ids.
- **Family management (P2)** — all in `src/db.cjs`, all mutating *membership* operations run in a transaction that **locks the `families` row first, then `users` rows** (one lock order everywhere, no deadlocks) and re-checks the caller is still the creator *after* taking the lock, so concurrent leave/remove/transfer can't act on stale state. Routes: `POST /api/family/leave` (any member; a creator with other members gets 400 "transfer first"; a creator who is the only member leaves = dissolves, response `dissolved:true`), `DELETE /api/family/members/[id]` (creator; 404 if the target isn't in the caller's family, 400 if it's the caller), `POST /api/family/transfer` `{userId}` (creator; strict positive integer, target must be a member; **also revokes the old creator's unused family invite codes**), `POST /api/family/dissolve` `{name}` (creator; `name` must equal the family name exactly), `PATCH /api/family` `{name}` (creator; trimmed, 1–100 chars, globally unique; updates the denormalized `family_name` on the family's receipts and items), `DELETE /api/family/applications/[id]` (applicant withdraws *their own pending* request — the row is deleted; 404 for anyone else's or an already-decided one), and `GET /api/family/me` now also returns `userId` and, for someone not in a family, `myApplications`. **Leaving in any form (leave/remove/dissolve) detaches the person's receipts and items** — `family_id`, `family_name` cleared, `account_type='individual'`, `user_id` untouched — so receipts follow the person (`detachUser`/`dissolveInTx`). Dissolving also deletes the family's pending requests and family invite codes via FK cascade, and the name becomes reusable. "Creator revokes an invitation" needs no new route: invite-by-username takes effect immediately, and family invite *codes* are revoked through `DELETE /api/invites/[id]`. `deleteUser()` (admin) now dissolves any family the user created first, so other members become individuals cleanly instead of keeping a stale `account_type='family'`.
- **`app/api/feedback/route.js`** — auth-gated: submit free-text feedback, or list *only your own* past submissions (not a public board). **`app/api/admin/feedback/route.js`** — admin-only, all users' feedback with the submitter's username.
- **`app/api/invites/**/route.js`** — auth-gated invite codes. `GET /api/invites[?kind=family|personal]` lists *only your own* codes with a derived status (`unused`/`used`/`revoked`/`expired`, plus the username that used it); `POST /api/invites` body `{ family: true }` creates a code — **strict boolean**, `"false"` is a plain code. A normal-tier account or an admin may create a plain code (**open-tier accounts get 403** — see the abuse note in Scope Boundaries); a **family code** (`invite_codes.family_id` set, registrant joins that family on signup) requires `session.familyId && session.isFamilyCreator` → else 403. Codes are 16 random bytes base64url, single-use, valid 7 days (`INVITE_VALID_DAYS`), and each user may create at most 20 codes per rolling 7 days (`INVITE_MAX_PER_WINDOW` / `INVITE_WINDOW_DAYS`) counting **every** code — used, revoked or expired too, so using or revoking one never frees a slot — enforced under `SELECT ... FOR UPDATE` on the user row → 400. `DELETE /api/invites/[id]` revokes your own unused code (404 for anyone else's, 400 if already used; revoking twice is idempotent). `[id]` segments go through `parseId()` (`src/http.js`: digits only, else 400) instead of a bare `+id`, which turned `1abc` into `NaN` bound into SQL — every `[id]` route (receipts, admin receipts/users, family requests, invites) uses it. UI: `components/InviteCodes.js` (shared list/generate/copy-link/revoke), opened from the header as `InviteModal` (plain codes) and from `FamilyPanel` (family codes, creator only). The copied link is `/login?mode=register&code=<code>`; `app/login/page.js` reads `?code=` and `AuthGate` pre-fills it.
- **Registration (`app/api/auth/register/route.js`)** — two paths. *With `inviteCode`*: `dbApi.peekInviteCode()` pre-checks (read-only) so form validation can run before anything is created; then `dbApi.registerWithInvite()` does user insert + code consumption (+ family join for a family code) in **one transaction that first locks the code row `FOR UPDATE`**, so concurrent signups with one code yield exactly one success. No captcha. The account is `signup_source='invite'`, `scan_tier='normal'`, `invited_by=<code creator>`. A family code ignores the form's family fields; a plain code still honours them. All code-invalid reasons (unknown/used/revoked/expired/non-string) return the *same* 400 message so code state can't be probed. *Without*: captcha required, `createUser(..., { signupSource: 'open' })` → `signup_source='open'`, `scan_tier='open'`. `signupSource`/`scanTier`/`isAdmin` in the request body are always ignored.
- **Scan quota (`app/api/scan/route.js`)** — after `checkImage` and before the billed call: `dbApi.reserveScan(userId, model, limit)` inserts a `scan_log` row *first*, then counts that user's rows in the last **rolling 24 hours** (not a calendar day — avoids timezone questions) and deletes its own row + returns 429 if the count exceeds `limit` (same insert-then-count order as the login lockout, so a concurrent burst can't exceed the limit). `limit` comes from `config.scanQuota[session.scanTier]` (`open: 3`, `normal: 20`); **admins are unlimited but still logged**. `finishScan(id, success)` records the outcome; failures count too (OpenRouter bills them). Rejected requests leave no row. `scan_log.success IS NULL` = in flight (a crashed request keeps counting). `users.scan_tier` is refreshed from the DB each request (`getAuthedSession` → `session.scanTier`), so an admin upgrade applies immediately. Existing accounts migrated to `signup_source='invite'`, `scan_tier='normal'` (column defaults). Admins change a tier with `PATCH /api/admin/users/[id]` `{ tier: 'open'|'normal' }`; `listUsers()` returns `signup_source`, `scan_tier`, `inviter_username` for the admin Users tab. Note: tests must seed `scan_log` timestamps with SQL `NOW() - INTERVAL`, never JS `Date` (mysql2 serializes in the machine's timezone, MySQL in its own).
- **`app/api/admin/**/route.js`** — admin-only, gated by `requireAdmin()` (`src/session.js`, 401 if not logged in / 403 if not `session.isAdmin`) instead of `requireSession()`. Mirror the regular `receipts`/`stats` endpoints but call the *same* `src/db.cjs` functions with `scope` omitted (global, across all users) or set to `{ userId: <admin-chosen target> }` (drill-down) — see `dateFilter`'s scope note below. Plus admin-only reads: `users` (`dbApi.listUsers()`, now includes each user's `family_name`/`family_role`), `stats/by-user` (`dbApi.statsByUser()`, spend-per-user, a dimension that doesn't exist in the single-user view), `feedback` (above). `users/[id]` `DELETE` refuses to delete the currently-logged-in admin (`+id === session.userId` check) to avoid self-lockout.
- **`app/uploads/[...file]/route.js`** — replaces the old `express.static('/uploads')`. Streams a file from `UPLOAD_DIR` (`src/uploads.cjs`). **Auth-gated per receipt**: the file name must match `saveImage()`'s shape (`^[A-Za-z0-9_-]+\.(jpg|jpeg|png|webp|gif)$` — single segment, which is also the path-traversal guard), the caller must be logged in (`getAuthedSession()`), and `dbApi.findImageOwner(name)` must find a receipt whose `user_id` is the caller, whose `family_id` equals the caller's current family, or the caller is admin. Every failure (not logged in, no permission, orphan file, bad name, missing file) is the same **404** so file names can't be probed. Responses carry `Cache-Control: private, no-store` — required behind Cloudflare, which edge-caches `.jpg` etc. by default and would otherwise serve one user's receipt to anyone. Deliberately at `app/uploads/...`, not under `app/api/...`, so image URLs (`/uploads/<file>`) are unchanged; `<img>` tags send the session cookie same-origin.
- **`src/session.js`** — `iron-session` config + `getSession()` (reads/writes the encrypted session cookie via `next/headers` `cookies()`) + `getAuthedSession()` + `requireSession()`/`requireAdmin()`/`requireFamilyCreator()` (the shared 401-or-session / 401-or-403-or-session helpers used by every protected/admin/family-management route). The cookie is only trusted for **identity** (`userId`). `getAuthedSession()` — which all three `require*()` helpers and `/api/auth/me` go through — does one primary-key query per request (`dbApi.getSessionUser()`, `users LEFT JOIN families`) and overwrites `isAdmin`/`familyId`/`familyName`/`familyRole`/`accountType`/`isFamilyCreator`/`scanTier`/`mustChangePassword` on the in-memory session object with the database's current values (the cookie itself is not rewritten). So revoking admin, joining a family (invited or approved) and deleting an account take effect on the very next request; a deleted account's cookie is destroyed and treated as logged out. Login/register still write those fields into the cookie, but nothing authorizes off the cached copies. Route code must keep reading permissions from the session returned by `require*()`/`getAuthedSession()`, never from a bare `getSession()` (only login/register/logout use that). `secure` comes from `COOKIE_SECURE=true` (set it for the public HTTPS deployment; leave it `false` for plain-HTTP localhost, where Safari would otherwise drop the cookie). No session table in MySQL.
- **`src/http.js`** — `wrap()` (uniform `{error}` responses; a thrown `HttpError(status, message)` keeps its status, anything else is 500), `clientIp(request)` (`CF-Connecting-IP`, else first `X-Forwarded-For`, else `null`), `readJson(request, maxBytes)` (capped streaming JSON body reader) and the `FORM_BODY_MAX` / `IMAGE_BODY_MAX` / `EDIT_BODY_MAX` constants.
- **`src/captcha.cjs`** — registration-page human check (tokens are single-use and wrong answers burn them, see the open-registration abuse-limits bullet; the signing key is `SESSION_SECRET` when it is at least 32 characters, otherwise a random per-process key — never a constant in the code, so tokens can't be forged; likewise `seedAdmin` refuses the `.env.example` placeholder password `change-me-admin`): `generate()` picks a random single-digit `+`/`-` expression, hand-renders it as a noisy SVG (per-character random rotation/position/color + decoy lines/dots, no image library, no third-party captcha service) base64'd into a `data:image/svg+xml` URI, and signs `answer:expiresAt` with `SESSION_SECRET` (HMAC-SHA256) into an opaque token returned alongside the image — the answer is never sent as readable text/JSON, only baked into pixels. `verify(token, answer)` re-derives the signature (`crypto.timingSafeEqual`) and checks the 5-minute expiry. Stateless by design (no server-side store of open challenges); `app/api/auth/register/route.js` calls `verify()` before touching the DB.
- **`src/openrouter.cjs`** — builds the vision prompt (in Chinese, matching the product's audience) sent to the configured OpenRouter model, calls `chat/completions` with the image as a data URL, extracts/repairs JSON from the model response (`extractJson`), then `normalize()`s it: clamps categories to the configured whitelist, backfills missing `unit_price`/`subtotal`/`total` by cross-deriving from other fields, coerces `taxable` to 0/1. `normalize()` is exported and unit-tested directly by `tests/normalize.test.js` without hitting the network. Unchanged by the Next.js migration except for the `__dirname`→`require()`/`process.cwd()` fixes noted above.
- **`src/db.cjs`** — owns a `mysql2/promise` connection pool to the external MySQL database and schema (`users` 1—N `receipts` 1—N `items`, plus `families`, `family_join_requests`, `feedback`, `login_failures`, `invite_codes`, `scan_log`, `admin_audit_log`, `captcha_used`, `signup_attempts`; cascade delete via `ON DELETE CASCADE` throughout). The pool is memoized on `globalThis.__vanspendPool` so `next dev`'s hot-reload doesn't leak a new pool (and exhaust MySQL connections) on every file save. ### Data flow for a receipt

1. Frontend posts the image as a base64 data URL to `POST /api/scan` → `openrouterLib.scanReceipt()` → normalized `{receipt, items, raw}`, **not yet persisted**.
2. User reviews/edits the extracted line items in the editable table (`ScanTab`) — AI misreads are expected and must be caught here, there is no offline OCR fallback.
3. Frontend posts the (possibly edited) `{receipt, items, image}` to `POST /api/receipts` → image is base64-decoded to a file in `uploads/` (`saveImage()`, `src/uploads.cjs`); before this, `ScanTab` asks `GET /api/receipts/duplicates` and shows a non-blocking `confirm()` if a same store/date/total receipt is visible (P3); the route calls `dbApi.saveReceipt(receipt, items, { stampFamilyFromDb: true })`, which **ignores any family fields from the caller or the request body** and, inside the transaction, takes a shared lock on the user's family row, re-reads the user's *current* `family_id`/`family_name`/`family_role` with locking reads (retrying if it changed while waiting) and stamps receipt + every item with them. This matters because the route reads the session before parsing the (up to 16 MB) body: stamping from the session would let a leave/remove/rename/dissolve in that window leave a receipt visible to a family the user is no longer in, with a stale family name, or fail the FK (500) after a dissolve. Family-management operations take the family row's exclusive lock, so they wait for an in-flight save, and a save that starts after them sees the new state. Without the option (tests, scripts) the caller's values are used as before.
4. `DashboardTab` reads aggregates from the `/api/stats/*` endpoints, all of which accept optional `from`/`to` date-range query params and are scoped by `memberScope(session)`: the caller's family (if any) plus the caller's own receipts, else just the caller's.

### Domain-specific rules to preserve

- GST/PST splitting follows BC-specific tax rules (5%/7%); when a receipt only prints a combined tax line, the app estimates the 5/7 split rather than guessing — this logic lives in the AI prompt (`openrouter.cjs:buildPrompt`), not in code.
- `name_norm` (AI-normalized item name) is what powers cross-time price trend matching (`priceTrend`, a `LIKE '%name%'` substring match on `name_norm`/`name_raw`) — it's inherently fuzzy since it's model-generated, not a canonical SKU.
- API error shape is always `{ error: string }` with a matching status: 400 bad input, 401 not logged in, 403 not admin / not family creator / an admin trying to self-delete / `password_change_required` (an extra `code` field, see P4), 404 not found *or* not allowed to see it (`/uploads`), 413 body/image too large, 429 login locked, 500 thrown errors. `wrap()` turns a thrown `HttpError(status, message)` (`src/http.js`) into that status and anything else into 500. Read request bodies with `readJson(request, maxBytes)` (`src/http.js`, streams with a hard cap → 413, bad JSON → 400; `FORM_BODY_MAX` 16 KB for forms, `IMAGE_BODY_MAX` 16 MB for image routes) rather than bare `request.json()` — used by **every** route that reads a JSON body (any other route should do the same); valid JSON that isn't an object (`null`, arrays, numbers) is also a 400.

## Trust model (public deployment)

The app runs on the public internet behind a Cloudflare Tunnel; anyone can reach `/` and `/login`, and anyone can register (invite code, or open registration with a captcha).
- **Anonymous visitors** can load the landing/login pages, fetch a captcha, register and log in (rate-limited by the login lockout; registration has no per-IP limit — see the captcha known gap). Every other endpoint answers 401, **including `/api/config`** (it exposes the model name and whether an OpenRouter key is configured; it became login-only in P5), and `/uploads/*` answers 404.
- **A registered user** sees only their own receipts, plus — if they are in a family — receipts saved while a member of the same family (read-only; editing/deleting stays owner-only). Receipts saved before joining a family stay private. They can edit/delete their own receipts, delete their own account (all their data and image files go), and spend a limited number of billed scans per rolling 24 h (3 for open registrations, 20 for invited ones, admins unlimited).
- **The site admin is fully trusted.** The single `is_admin` role (bootstrapped from `ADMIN_USERNAME`/`ADMIN_PASSWORD`) can read and delete every user's receipts and images, delete any account, reset a password to a temporary one, change scan tiers, and read all feedback; every admin *write* is recorded in the read-only `admin_audit_log`, reads are not. The landing page says this to users (the data section). There is no impersonation, no co-admin, and the admin password is not changeable in-app.
- **The operator** (whoever runs the server) can read the database and `uploads/` directly; receipt images are sent to OpenRouter's model for each scan. There is no end-to-end encryption and no export feature.
- **Network rules**: the app port is bound to `127.0.0.1` only and public traffic arrives through the `cloudflared` service, which is what makes `CF-Connecting-IP` trustworthy for the login lockout; the MySQL server must never be reachable from the internet; `COOKIE_SECURE=true` is mandatory on the public deployment (plain-HTTP localhost keeps it `false`). Sessions are stateless cookies (no force-logout; deleting the account or the admin resetting the password gates every device).
- **Hostile-input assumptions**: every request body is read with a size cap, ids are validated, every query is parameterised, image uploads are whitelisted by data-URL type and size, authorisation is re-read from the database on every request, and every permission rule has a positive and a negative test. Known gaps that a determined attacker could use are listed under *Known trade-offs and risks* (slow open-account farming from many IPs, invite trust chain, not rate-limited password endpoints, rare family-operation deadlock 500s).

## Scope Boundaries

**Known trade-offs and risks**
- AI extraction is not 100% accurate; the manual review/edit step before save is a required control, not optional UX polish.
- Tax split (GST/PST) is estimated by ratio when a receipt only prints one combined tax total.
- Cross-time price comparison relies on fuzzy `name_norm` matching.
- Editing a receipt always recomputes `subtotal`/`total` from the items, so a receipt whose printed total differs from the item sum (rounding, a discount not itemised) loses the printed total on its first edit; the original AI read stays in `raw_json`. Editing replaces the items rows wholesale (new ids), and an edit is last-write-wins (no version check) — only the owner can edit, so concurrent edits mean the same person on two tabs.
- Every scan costs an OpenRouter API call (billed, though cheap with the default Gemini 2.5 Flash model).
- Session cookie is signed/encrypted but stateless (`iron-session`) — no server-side way to force-invalidate one *specific* session before its cookie expires (no "log out all devices"; changing the password doesn't log out other devices). Permissions and family membership are re-read from MySQL on every request (one extra primary-key query per request), so they no longer lag; deleting the account is the only way to kill all of a user's sessions at once.
- Login lockout (`app/api/auth/login/route.js`): 10 failures within 15 minutes for the same username **or** the same IP lock that key for a **fixed 15 minutes from the 10th failure** (429, even with the right password). `dbApi.isLoginLocked` finds the key's latest failure L inside the window and counts failures in (L−15 min, L]; locked requests write nothing, so L doesn't move and the lock lasts exactly 15 minutes. **Order matters (race fix):** the route checks the lock, then *records the attempt first* (`recordLoginFailure` returns its id), then counts (`countRecentLoginFailures`), and only if the count is ≤ 10 runs bcrypt — otherwise it deletes its own row (`deleteLoginAttempt`) and returns 429. Counting before recording would let a concurrent burst all read 0 and each get a guess. A failed password keeps the row; success clears that username's rows (`clearLoginFailures`), not the IP's. Rows live in `login_failures` (pruned after a day on each insert; username/IP truncated to the column widths 100/64 so oversized input can't 500). IP comes from `clientIp()` (`src/http.js`): `CF-Connecting-IP`, else the first `X-Forwarded-For` entry (Route Handlers can't see the socket address; Next only fills XFF from the socket when the client didn't send one, so this fallback is client-spoofable and is only reached when the request didn't come through the Tunnel), else `null` → the IP dimension is skipped for that request rather than lumping everyone into one bucket. In local dev every request usually shares `::1`, so 10 failures lock the whole machine out for 15 minutes. Anyone can deliberately lock a known username (including the admin) for 15 minutes. `/api/auth/password` (current-password check) is not rate-limited.
- Images: `uploadsLib.checkImage(image)` (`src/uploads.cjs`) rejects anything that isn't a string `data:image/(png|jpeg|jpg|webp|gif);base64,...` with 400 (so `data:image/html` or `svg+xml` can't be written to disk) (an array-wrapped image used to pass the size check as 0 bytes while `saveImage`'s regex still matched it) and a decoded size over 10 MB with 413. `/api/scan` and `/api/receipts` call it before the billed OpenRouter call / before writing to disk, and `saveImage()` independently refuses non-strings and oversized input. `ScanTab` re-encodes images whose long edge exceeds 2000 px to JPEG (quality 0.85) in the browser first; formats the browser can't decode (e.g. HEIC in some browsers) are uploaded as-is.
- `next build` meaningfully increases Docker image size/build time versus a zero-build static-file image.
- The admin console can view/delete any user's receipts and delete any user account (cascades their data) — real destructive cross-user power, no undo (since P4 each such write is recorded in the read-only `admin_audit_log`, but it records who did what, it does not undo it).
- Joining a family (invite or approved apply) grants read access to every other member's receipts/items/stats — a member who shouldn't see someone else's spending has no finer-grained opt-out short of leaving the family (built in P2: leaving takes your receipts with you, and receipts saved before you joined were never shared).
- The registration-page captcha is a self-hosted, low-cost deterrent (a single-digit arithmetic problem rendered as a noisy SVG), not a hardened anti-bot service — it raises the bar over a bare form but won't stop a determined/targeted attacker the way a commercial captcha service would. Its SVG also bakes in a dark background (`src/captcha.cjs`), which now shows as a dark slab on the light `/login` card.
- Two visual languages coexist: the marketing landing page and `/login` are light (Apple-ish, `landing.css`), the logged-in app is dark (`globals.css`). Logging in is a deliberate one-time jolt between them, not an oversight.
- The landing page's charts/ledger/amounts are hardcoded illustrative mockups (badged 示例/Sample), not live data. Its copy is written to match what the app actually does — including saying out loud that scanning sends the image to OpenRouter. **Don't add a marketing claim without checking the code supports it**; the source design doc promised on-device photos, E2E encryption, CSV export, self-learning categories and a 6-member cap, none of which exist.
- The landing page and register form must stay truthful about the two registration paths (invite code → normal quota; open registration with a captcha → lower quota until an admin upgrades the account), the data-location/admin-visibility statements and the "no export" fact; P5 rewrote them and `tests/landing-copy.test.js` fails if the quota numbers or those claims drift from `config/config.json`/the code. The register form's own hint texts live in `components/AuthGate.js` and `components/LoginClient.js`, not in `copy.js` — check them by hand when registration rules change.
- **Invite-code abuse model (decided after verification found an amplification hole).** Invite signup skips the captcha and grants the normal quota, so if *any* account could mint codes, one captcha solve would roll out unlimited captcha-free normal accounts (20 per account per generation). Mitigations in place: accounts on the `open` tier cannot mint codes (admins can; an admin must upgrade a user first), and every account is capped at 20 codes per rolling 7 days counting used ones. What remains is a **trust chain**: a normal-tier account that goes rogue can still recruit ~20 accounts a week, and each of those can recruit 20 more. The admin Users tab shows who invited whom (`inviter_username`) and can downgrade an account to `open`, which stops its minting but does not revoke codes it already issued. No IP-based registration limit, no account-age gate. A valid code can also probe whether a username exists (a taken username returns 400 without burning the code) — the open path allows the same, one captcha per probe.
- **Open-registration abuse limits (post-P5 hardening; was a known gap through P5):** a captcha token is **single-use** — after the signature/expiry/answer check the route records `sha256(token)` in `captcha_used` (primary key, so a concurrent double use yields exactly one success), and a token with a valid signature but a *wrong answer* is also burned (the answer is a one-digit sum/difference, ~27 possibilities, so otherwise one token could be guessed repeatedly); garbage tokens are not stored. A used token or username-taken failure therefore always needs a new captcha, so a username can't be probed more than once per captcha. Additionally each client IP (`clientIp()`: `CF-Connecting-IP`, else first `X-Forwarded-For`, else none → skipped) gets at most **10 open-registration attempts that passed the captcha per rolling 24 h** (`signup_attempts`, `reserveOpenSignup`: insert, then count, then delete its own row if over — the same fail-closed order as login lockout and scan quota, so a concurrent burst never exceeds the limit but may reject a few under it); over the limit → 429. Failed attempts (taken username) count; requests that fail the captcha, and invite-code registrations, don't. Each open account still gets 3 billed scans/day, so a determined attacker with many IPs can still farm accounts slowly (~10/IP/day); there is no account-age or email gate. Shared NAT users can hit the per-IP cap (then use an invite code). Old rows are pruned on write (`captcha_used` after 10 min, `signup_attempts` after 2 days).
- **Known family-management gaps (found in P2 verification, none corrupt data):** `inviteMember`, `decideRequest` and `registerWithInvite` don't take the family row lock, so approving a request or a family-code signup racing a dissolve can hit an InnoDB deadlock and return 500 (nothing is committed; a retry works); `decideRequest` checks the caller is creator *before* its transaction and doesn't re-check under a lock, so a creator who has just transferred can still decide one request already in flight; `decideRequest` reports success even when the applicant has meanwhile joined another family (the join `UPDATE` matches 0 rows); `dissolveInTx` clears items by `family_id`, so a legacy item whose `family_id` differs from its receipt's is not repaired (unreachable with data written by current code).
- Concurrent scans fail closed: `reserveScan` inserts before counting, so several simultaneous scans can all see each other's pending rows and be rejected even though the user is under quota (never over). A rejected scan leaves no row and costs nothing.
- Both languages of the landing page ship at once, so there are two copy sets to keep in sync (the test checks they have the same structure, not that the translations say the same thing).

**Strict constraints**
- Requires a reachable external MySQL server; `MYSQL_*` credentials live in `.env` (never commit real credentials).
- Public deployment via Cloudflare Tunnel is the supported setup (GitHub issue #1, phases P0–P5, all done): never publish the app port or MySQL beyond loopback/the compose network — the MySQL server must not be reachable from the internet, and `COOKIE_SECURE=true` is mandatory. The full trust model is in the *Trust model* section above.
- Receipt images (`uploads/`) remain local disk files, not stored in MySQL. `/uploads` is authorized per receipt (owner / same family / admin, else 404) — see the `app/uploads` bullet above.
- Registration is open: either by invite code (a normal-tier account or an admin may generate codes, no approval) or without one (captcha-guarded, low daily scan quota, no approval — an admin can raise the quota). Exactly one elevated role (`is_admin` boolean, no finer-grained permissions), grantable only via the `ADMIN_USERNAME`/`ADMIN_PASSWORD` bootstrap — never through the registration API. Joining a *family* is the one place something does require approval: an apply request sits pending until the family's creator (and only the creator — not just any member) approves or rejects it; an invite from the creator, by contrast, takes effect immediately.
- Exactly one creator per family, and only the creator can invite, approve/reject applications, remove members, transfer the creator role, dissolve or rename the family. Creatorship moves only by an explicit transfer to another member; a creator cannot leave while other members remain; there is no co-admin role.
- Plain JS/JSX, no TypeScript, no ESLint config, no state-management library, no CSS framework. No i18n library either — the landing page's bilingual copy is a plain `{zh, en}` object in `components/landing/copy.js`, and only the landing page is bilingual (the login form, the app and `/admin` stay Chinese).
- No static asset directory: there is no `public/`, and the Dockerfile only copies `.next/standalone`, `.next/static`, `config/` and `sql/`. Every landing visual must stay pure CSS / inline SVG / emoji — an image or webfont would 404 in the Docker image.

**Explicitly not included**
- No editing receipts/line-items from the admin console (view + delete only); owners edit their own receipts from the normal UI (P3).
- No "re-scan the original image" from the edit screen, no edit history/audit trail, no editing of the currency, the image, or which family a receipt belongs to, and no duplicate *blocking* or fuzzy duplicate matching (store text, date and total must match exactly; the store comparison is trim + case-insensitive only).
- A temporary password has no expiry (valid until the user changes it); an admin can delete another admin (only self-deletion is refused, and `seedAdmin` recreates the `.env` admin on restart); `adminDeleteReceipt` locks only the receipt row (`FOR UPDATE OF r`) — a version that also locked the owner's `users` row deadlocked with family operations in verification. Admin `deleteUserFull` vs concurrent family operations can still hit the documented rare InnoDB deadlock 500 (retry works); a receipt save racing a self/admin account deletion can return a 500 (FK) and leave an orphan image file that `/uploads` 404s.
- The audit log covers only admin *writes* (delete user, delete receipt, reset password, set tier) — no view logging, no log of users' own actions, no retention/export UI; no "log in as" / impersonation flow.
- No in-app admin creation/promotion UI or self-service admin password change.
- No email field, email verification or emailed password recovery: the only recovery path is an admin resetting a password to a temporary one and telling the user out of band. No self-service "forgot password"; no password-strength rules beyond "new ≠ current"; admin accounts can neither be reset nor self-delete (they come from the `.env` bootstrap).
- No pricing/paid tiers anywhere (deliberately dropped from the source design), no server-rendered or crawlable landing page (`/` still renders nothing until the client's `/api/auth/me` resolves), no OG/SEO metadata, no `/en` route, and no redirect away from `/login` for an already-logged-in visitor.
- No cloud backup/sync of `uploads/`.
- No budgets/alerts, no income tracking, no PDF/Excel export.
- No batch receipt import or bank/credit-card statement reconciliation.
- No offline OCR fallback.
- No server-side rendering/data-fetching optimizations — everything stays client-rendered (`"use client"`), same as the original SPA.
- No connection-pool tuning, retry/backoff, or migration framework beyond `schema.sql` + the app's own `CREATE TABLE IF NOT EXISTS` / column-backfill migrations.
- No admin UI for family management (an admin can only delete the underlying user account, which dissolves a family that user created); no family-level approval for leaving; no "ban" list — a removed member can re-apply or be re-invited; no ownership transfer of a *receipt* between members.
- No history sharing when joining: a user's receipts from before joining stay private (visible only to them); there is no "share my past receipts with the family" action.
- No write-sharing inside a family — editing or deleting a receipt is always owner-only, regardless of family membership.
- No email/push notification when invited, applied-to, approved, or rejected — the invitee/applicant only finds out by checking the "家庭" tab (or, for an invite, by the fact that their next page load now shows a family — session permissions are re-read from the DB on every request).
- No reply/status/resolution workflow on feedback — it's a one-way box (user writes, admin reads); no threading, no marking resolved, no notifying the submitter back.
- No image-based (photo) captcha, no third-party captcha service (reCAPTCHA/Turnstile/hCaptcha) — see the self-hosted-SVG trade-off above.
